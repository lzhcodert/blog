XX银行 CRM 系统架构：三条通道与一条数据主链

这份整理来自两段对话。对话先各自产出了一份文档——一份讲「分层架构与上下游调用」，一份讲「系统交互流转」——本文把两份文档合并成一篇，去掉重复，只留下真正需要记住的部分。

## 整体判断

整个系统可以压缩成一句话：**CRM 负责业务操作，数据集市负责把通用数据加工成「即取即用」的专用数据，两者之间靠三条通道连接。**

三条通道各司其职，不要混着看：

- **ESF / ESB 服务总线**——管实时服务调用，同步、秒级返回，负责路由、协议/报文转换、鉴权与流控。
- **数据交换平台（DataStage）**——管数据流转的双向摆渡，异步批量为主，遵循「交易与批处理分离」。
- **信创 OBS 对象存储**——管非结构化文件的海量承载，CRM 数据库里只留文件引用地址（URL），不落地文件本体。

## 分层与调用

从下往上看四层：源系统层提供客户/账户/交易/交互的原始数据，经 ETL 进入数仓；通道层把实时、批量、文件、触发四类能力横向铺开；数据与服务层里，数仓按 ODS → DWD → DWS 逐级汇总，数据集市再从 DWS 取数加工成宽表、标签与模型；最上层是 CRM 的客户视图、精准营销名单和业绩看板。

调用方向上有三种线：**实线双向**是同步实时调用（CRM ⇄ ESF/ESB ⇄ 微服务群）；**实线单向**是上报入湖（CRM → 数交 → 数据湖/数仓）；**虚线**是集市加工结果异步回供 CRM 落库，以及文件就绪/消息这类触发信号。

## 数据加工与消费链路

这里最容易误读成双向。实际上主链是**单向**的：

源系统 / 数仓 → ODS → DWD / DWS → 数据集市 → CRM 消费

数据集市是核心环节。它从数仓汇总层取数，按 CRM 的分析需求加工成业务宽表、画像标签和营销模型，把通用数据转成 CRM 专用的「即取即用」数据；CRM 只负责消费，驱动客户视图、精准营销名单和业绩看板。

这条单向链和上面那张双向摆渡图并不矛盾——它描述的正是「回供落库」这一支的内部过程。

## 三种触发机制

集市加工完成后，怎么通知数交开始调度？有三种做法：

- **文件就绪触发（最常用）**：集市产出数据文件后，再生成一个空的触发器文件，DataStage 的 `Wait for File` 阶段持续监测，发现文件即启动。稳健、易管理，适合 T+1 批量。
- **消息触发（准实时）**：集市完成后向 `MQ / Kafka` 发消息，DataStage 通过 WebSphere MQ 阶段或 Kafka/JMS 适配器消费并触发作业。适合时效要求高的场景。
- **调度平台触发（企业级）**：由 `TASKCTL / iMOIA.SMS` 集中管理，Agent 依据作业依赖触发，支持失败重试、告警与统一运维。

需要说明的是，并非所有取数都要等一天。实时营销名单、风险预警这类时效敏感场景，可以通过 API 同步调用或 MQ 准实时补充——但这类交互通常发生在 CRM 与后端微服务之间（经 ESF/ESB），用于查询单个客户的实时状态；数据集市的核心产出绝大多数仍以批量异步交付。

## 完整场景串一遍

客户经理在 CRM 点击「查看全景画像」→ 经 ESF/ESB 实时调用客户/账户微服务，秒级聚合返回；同时，交互行为数据经数据交换平台批量入湖 → 数据集市加工成画像标签与营销名单 → 再经数交异步回供 CRM 落库，用于优化次日营销；过程中生成的报告或录音经 API 存入信创 OBS，数据库内仅保留引用地址。

一句话概括：**ESF/ESB 管「服务调用」的实时控制，数据交换平台管「数据流转」的双向摆渡（异步批量为主），信创 OBS 管「文件存储」的海量承载。**

## 术语速查

| 缩写 | 全称 | 作用 |
|---|---|---|
| ODS | 操作数据存储层 | 最靠近源系统，存放 ETL 抽取的原始数据快照 |
| DWD / DWS | 明细层 / 汇总层 | 清洗去重后的明细事实；按主题轻度汇总的宽表 |
| 数据集市 | Data Mart | 从 DWS 取数加工成宽表/标签/模型，供 CRM 即取即用 |
| ESF / ESB | 微服务平台 / 企业服务总线 | 服务路由、协议转换、鉴权与流控 |
| DataStage | IBM ETL 工具 | 数交平台的核心 ETL 引擎，负责批量加工与调度 |
| OBS | 对象存储 | 承载录音、转写、报告等非结构化数据 |
| T+1 | 交易日次日 | 银行批处理常见口径，当日数据次日加工完成 |
