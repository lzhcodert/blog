缓存出事的时候，告警长得都差不多：**数据库 QPS 突然涨、接口变慢、连接池快打满**。

但根子可能完全不同。有人连夜加 Redis 节点，有人急着上布隆过滤器，还有人把 TTL 全改长——结果药不对症。

先把三句话记住：

- **穿透**：查的数据**根本不存在**，缓存里没有，数据库里也没有，但请求还源源不断地来。
- **击穿**：一个**特别热的 key 恰好过期**，几十万请求同时发现缓存没了，一起扑向数据库。
- **雪崩**：**一大片 key 同时过期**，或者缓存集群整体挂了，所有请求一起失去保护。

再压成一句更好记的：**穿透是"查无此人"，击穿是"一个人恰好下班"，雪崩是"整条街同时停电"。**

> 说明：这三个词主要是中文工程圈的说法。Redis 官方博客里更常看到 **cache stampede / thundering herd**（对应击穿）和 **cache avalanche**（对应雪崩）；"穿透"在英文资料里通常归入"查询不存在的 key 导致反复 cache miss"，用空值缓存或布隆过滤器来讨论。

## 先把基准线立住：缓存本来是怎么挡数据库的

绝大多数系统用的是 **Cache-Aside（旁路缓存）**：

1. 应用先读缓存。
2. 命中就直接用，数据库完全不知道这次请求。
3. 未命中才查数据库，查完顺手写回缓存，设一个 TTL。
4. 下一次同样的请求就能命中。

所以缓存能挡住数据库，靠两个前提：

- **缓存里有这个值**；
- **用户查的值在数据库里确实存在**。

三种事故，本质上就是把这两个前提打破：

| 被打破的前提 | 对应事故 |
|---|---|
| 数据库里压根没这个值 | 穿透 |
| 有这个值，但缓存刚好空了一瞬 | 击穿 |
| 一大批值同时没了，缓存层整体失守 | 雪崩 |

## 穿透：数据库反复被问"这个人存不存在"

### 它到底是什么

假设你有个商品详情接口 `/product?id=1001`。

正常用户查 `1001`，缓存有就返回。但爬虫或者攻击者开始查：

```text
id = -1
id = 99999999
id = "abc"
id = 1001' OR '1'='1
```

这些 key 在缓存里当然没有。请求就穿过缓存问数据库："有这个商品吗？"数据库查完回答："没有。"然后**这个"没有"没被记下来**。

下一个同样的请求来了，再查一次数据库；换个随机 id，又查一次。缓存形同虚设，数据库一直在干无效活。

> **穿透的关键不是"查不到"，而是"查不到这件事没有被记住"。**

### 为什么它特别容易被忽略

穿透不像雪崩那样轰然倒下。它常常表现为：

- 数据库 QPS 比平时高一点，但没到告警线；
- 慢查询里看不到特别吓人的 SQL；
- 缓存命中率缓慢下降，而不是断崖式下跌；
- 日志里大量请求返回"数据不存在"。

结果就是：大家盯着 CPU、连接数看半天，没发现有人在拿不存在的 id 反复敲门。

### 两道防线

**防线 1：布隆过滤器（Bloom Filter）**

在缓存前面放一个"门卫名册"。请求来了先问它："这个 id 可能存在吗？"

布隆过滤器的性格很特别：

> 它说"不存在"，那就**一定不存在**，直接拦掉；它说"存在"，只是**可能存在**，还要继续往下查。

Redis 官方文档对这种不对称性写得很直白：如果报告 absent，那肯定 absent；如果报告 present，还有很小概率其实 absent。也就是说，布隆过滤器**不会放过真正不存在的 key**（代价是可能误杀几个存在的 key，让你多做一次数据库查询）。

Redis 里可以用 Bloom 模块的命令：

```redis
BF.EXISTS product_filter 1001
```

返回 0 就直接返回空，连 Redis 缓存都不用查。

**防线 2：空值缓存**

数据库查出来是 0 行，也往缓存写一条占位值：

```text
product:1001 = null   TTL = 30~120 秒
```

下次同样的不存在 id 来了，缓存直接命中这个"查无此人"，数据库不用再被问。

Redis 官方的 Cache-Aside 实践文档也提到这一点：真实系统里可以为缺失记录缓存一个短 TTL 的 "not found" 哨兵，用来吸收探测不存在 ID 的流量；同时哨兵 TTL 要短于正常缓存，这样新建的记录才能尽快被看到。

### 这里有个坑

空值缓存的 TTL 不能太长。

比如商品 `1002` 现在不存在，你缓存了 `product:1002 = null`，TTL 设了 24 小时。结果运营 5 分钟后上架了这个商品，用户查一小时还是"不存在"——这就是自己制造的数据延迟。

**经验值**：空值 TTL 用 30~120 秒就够挡住突发探测，又不至于让新数据半天出不来。

## 击穿：一个热点 key 过期，几万人同时扑向数据库

### 它到底是什么

假设首页有个爆款商品 `product:1001`，每秒 5000 次请求，缓存命中率几乎 100%。

它的缓存 TTL 是 300 秒。第 300 秒那一刻，key 过期了。

在这一瞬间：

- 请求 A 发现缓存没了，去查数据库；
- 请求 B 也发现没了，去查数据库；
- 请求 C、D、E……一直到第 5000 个，都发现没了，都去查数据库。

数据库原本一秒只被问几次（缓存回源），现在一秒被问 5000 次，而且查的是**同一行数据**。

> **击穿的关键不是"数据不存在"，而是"同一时刻，同一个 key，大量并发回源"。**

Redis 官方博客把这种模式叫 **cache stampede / thundering herd**：一个热门缓存条目过期时，依赖它的用户全部回退到数据库，用并发查询把数据库压垮。

### 它和穿透到底差在哪

| 对比项 | 穿透 | 击穿 |
|---|---|---|
| 数据存在吗 | **不存在** | **存在** |
| 缓存里为什么没有 | 从来就没东西可存 | 恰好过期 / 被删 |
| 请求特征 | 很多不同的不存在 key | 大量请求打同一个 key |
| 持续时间 | 一直有，直到上防线 | 一波尖刺，回写后恢复 |
| 典型药方 | 布隆过滤器 + 空值缓存 | 单飞锁 + 逻辑过期 |

一句话：**穿透查的是"没有的东西"，击穿抢的是"同一份东西"。**

### 药方 1：互斥锁 / single-flight

核心思想：**同一时刻，只让一个人去查数据库，其他人等结果。**

Redis 里常用 `SET lock_key token NX PX ttl` 抢锁：

```text
抢到锁 → 查 DB → 写缓存 → 释放锁
没抢到 → 等一小会儿 → 再读缓存 → 拿到就返回
```

Redis 官方的 Cache-Aside 示例里用的就是这个思路：用 Lua 脚本原子地 `SET NX PX` 抢锁，只有拿到锁的任务去查主存储；其他任务短暂轮询缓存，等锁持有者写回。释放锁时还要校验 token，避免自己的锁超时后被别人续上、结果误删了别人的锁。

### 药方 2：逻辑过期 + 后台刷新

另一种思路更"用户友好"：**缓存值不真正删掉，只在里面记一个过期时间。**

- 请求来了，发现值"逻辑上过期了"；
- 先把旧值返回给用户，接口不卡；
- 同时异步起一个任务去查数据库、更新缓存；
- 下一个请求拿到就是新值。

Redis 官方在讲 cache stampede 时也提到 **probabilistic early expiration**（如 XFetch）：不等到真正过期，而是按概率提前刷新热 key，把回源动作错开。

两种药方怎么选：

- **不能接受旧数据**（比如库存、价格）：用互斥锁，宁可让用户等几十毫秒。
- **能接受秒级旧数据**（比如文章阅读数、首页推荐）：用逻辑过期，体验更顺。

## 雪崩：一大片 key 同时失效，缓存层整体失守

### 它到底是什么

雪崩有两种常见起因：

**起因 A：TTL 设得太齐。**

上线时图省事，所有缓存都写 `TTL = 300s`。于是它们在同一时刻集体过期。那一秒，命中率从 99% 掉到 0，所有请求一起找数据库。

**起因 B：缓存集群故障。**

Redis 主从切换失败、实例 OOM、网络分区、误执行 `FLUSHALL`……缓存整体不可用，所有请求同时失去保护。

Redis 官方博客对 cache avalanche 的描述就是：一次故障把整个缓存冲掉，恢复时所有请求一起打到后端；如果故障持续时间超过 TTL，缓存内容基本失效，后端就要承受全量冷启动负载。

### 它和击穿到底差在哪

| 对比项 | 击穿 | 雪崩 |
|---|---|---|
| 影响范围 | **一个**热点 key | **一大片** key，甚至整个缓存层 |
| 典型原因 | 单个 key 到期 | TTL 整齐、批量刷新、Redis 故障 |
| 恢复方式 | 回写一次缓存就好 | 要预热、要限流，恢复慢 |
| 典型药方 | 单飞锁、逻辑过期 | TTL 抖动、多级缓存、熔断、高可用 |

一句话：**击穿是单点爆，雪崩是全面爆。**

### 四层防线

**① TTL 抖动（Jitter）**

别让所有 key 活一样久：

```text
ttl = 基础值 + random(0, 抖动区间)
```

比如基础 300 秒，再加 0~60 秒随机值。这样 key 的过期时间散开，不会整点集体阵亡。

这是成本最低、最该先做的一条。Redis 官方在讲 stampede 和 avalanche 时都点名了 **TTL jitter**：随机化过期时间，避免大量 key 同时失效。

**② 多级缓存**

进程内缓存（比如本地 Caffeine / Go map）挡在最前面，Redis 挡在第二层。Redis 短暂抖动时，本地缓存还能顶一小会儿。

代价是本地缓存的失效要处理好：要么 TTL 更短，要么实例间广播失效消息，否则用户会读到各自的旧数据。

**③ 熔断与降级**

当数据库压力超标，直接"跳闸"：

- 返回兜底数据（比如"服务繁忙，稍后再试"）；
- 或者返回上一次缓存下来的旧值；
- 让数据库喘口气，别真挂。

Redis 官方把 circuit breaker 和 load shedding 列为缓存不可用时的最后防线：**宁可拒绝一部分请求，也别把后端彻底打死。**

**④ 缓存高可用**

主从、哨兵、集群、跨可用区部署，避免 Redis 自己成为单点。热点数据提前预热，别等流量来了才现装。

## 三者放一起对照

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 一句话 | 查无此人 | 一人下班，万人扑空 | 全城停电 |
| 数据存在吗 | 不存在 | 存在 | 存在 |
| 缓存为什么没挡住 | 没东西可存 | 单个热点过期 | 大片过期 / 缓存挂了 |
| 数据库承受什么 | 持续无效查询 | 瞬间尖刺 | 全量洪峰 |
| 命中率表现 | 缓慢下降 | 一个点掉下去又回来 | 断崖式下跌，恢复慢 |
| 首选防线 | 布隆过滤器 + 空值缓存 | 单飞锁 / 逻辑过期 | TTL 抖动 + 熔断 |
| 兜底防线 | 接口参数校验 | 热点预加载 | 多级缓存 + 高可用 |

## 术语小抄

| 术语 | 大白话 |
|---|---|
| Cache-Aside | 应用自己管缓存：先查缓存，miss 再查库并回写 |
| 命中 Hit / 未命中 Miss | 缓存里有没有你要的 key |
| 回源 | 缓存没命中，转去查数据库 |
| TTL | Time To Live，缓存条目活多久 |
| 缓存空值 | 把"查无此人"也当结果缓存一小会儿 |
| 布隆过滤器 | 省空间的"可能存在"名册：说没有一定没有，说有不一定有 |
| 误判率 False Positive | 布隆说"有"，其实没有的概率 |
| Single-flight | 同一时刻，同一个 key 只放一个人去回源 |
| 互斥锁 | 用 Redis `SET NX PX` 抢一个短暂的唯一通行证 |
| 逻辑过期 | 值不删，只在里面标"该刷新了" |
| XFetch | 按概率提前刷新热 key 的算法，不等真正过期 |
| Jitter | 抖动，在固定值上加随机数，把时间点打散 |
| 熔断 Circuit Breaker | 压力超标就跳闸，先拒绝一部分请求 |
| 降级 | 不返回完整结果，改返回兜底值或旧值 |
| 多级缓存 | 本地缓存 + 远程缓存两道防线 |
| 预热 | 流量来之前先把热点数据塞进缓存 |
| 热 key | 被极高频率访问的某一个 key |

## 生产上怎么定位：别三种药一起灌

告警响了，按这个顺序看：

1. **缓存命中率**：断崖跌 → 雪崩或击穿；缓慢跌 → 警惕穿透。
2. **DB QPS 曲线**：尖刺后迅速回落 → 击穿；一直高位 → 穿透；洪峰且久不恢复 → 雪崩。
3. **空值 key 比例**：突然变高 → 有人在探测不存在的 key，上布隆/空值缓存。
4. **锁等待数**：某个 key 的 single-flight 等待很多 → 热点 key 在打架。
5. **Redis 自身指标**：连接数、内存、主从切换、`evicted_keys` → 判断是否缓存层整体出问题。

定位清楚再动手：

- 查不到 → **空值缓存 + 布隆过滤器**；
- 一个热 key 过期 → **单飞锁 + 逻辑过期**；
- 大片 key 或缓存挂了 → **TTL 抖动 + 多级缓存 + 熔断 + 高可用**。

> 一个常见误区：把 TTL 全改成 24 小时"解决"雪崩。那只是把雪崩推迟到明天，还顺手制造了大量脏数据。**TTL 抖动**才是解法，不是"干脆不过期"。
