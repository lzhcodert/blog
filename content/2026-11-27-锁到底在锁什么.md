「这个变量要加锁。」

「这里得用分布式锁，不然多个节点会重复跑。」

这两句话在代码评审里出现频率极高。但真追问一句「锁的到底是什么」，很多人会卡住：是锁那行代码？锁那个变量？还是锁一个对象？单机锁和分布式锁又差在哪——不都是「同一时间只能一个人进」吗？

这篇按四个问题讲清楚：

1. 锁产生的背景是什么？没有锁会出什么事？
2. 锁的原理是什么？它凭什么能保证「同一时间只有一个人」？
3. 单机锁和分布式锁的区别在哪？
4. 什么时候需要锁，什么时候不需要？

先给一句话版本：

> **锁不是锁住代码，而是大家约定共同看一眼同一个「标记」：谁先把标记占上，谁干活；干完把标记还回去。**
> 单机锁的标记在**一个进程的内存里**，分布式锁的标记在**所有机器都能访问到的第三方存储里**。位置一变，麻烦就全变了。

全文用一家公司的会议室贯穿：同一间屋子、两拨人同时想进去，怎么定规矩。

## 一、背景：没有锁，到底会出什么事

不是所有共享都需要锁。只读的东西，一百个人同时看也不会看坏。锁是因为「**多个人同时改同一份东西**」才会被逼出来的。

Java 官方教程给过一个特别经典的例子，我照搬过来（原文叫 `Counter`）：

```java
class Counter {
    private int c = 0;
    public void increment() { c++; }
    public void decrement() { c--; }
}
```

看起来人畜无害。但 `c++` 这一行，在虚拟机里其实是**三步**：

1. 把 `c` 现在的值读出来；
2. 在这个值上加 1；
3. 把结果写回 `c`。

如果两个线程同时做，官方给了这样一条时间线：

| 时刻 | 线程甲 | 线程乙 | 内存里的 c |
|---|---|---|---|
| 1 | 读出 0 | | 0 |
| 2 | | 读出 0 | 0 |
| 3 | 算出 1 | | 0 |
| 4 | | 算出 -1 | 0 |
| 5 | 写入 1 | | 1 |
| 6 | | 写入 -1 | -1 |

甲加了一次、乙减了一次，结果本该还是 0，最后却是 -1。官方原话是：

> Interference happens when two operations, running in different threads, but acting on the same data, interleave.
> （两个跑在不同线程里、作用于同一份数据的操作**交错**时，就会发生干扰。）

而且「这次结果丢了」还是运气好的情况——官方也说了，换个时序可能是乙的结果丢，也可能完全不出错。**正因为时好时坏，这类漏洞极难排查。**

这还只是第一层。第二层更隐蔽：**你改了，别人根本看不见**。

官方对「内存一致性错误」的定义是：

> Memory consistency errors occur when different threads have inconsistent views of what should be the same data.
> （不同线程对「本该是同一份数据」看到了不一致的样子。）

翻译成会议室的话：甲在白板上改了日程，乙手里还拿着昨天抄的纸，按旧日程走进了屋子。多核 CPU 各有各的缓存，这种「各看各的」是真实存在的，不是理论假设。

所以锁其实要同时解决两件事：

- **互斥**：同一时间只让一个人进（防「交错」）；
- **可见性**：下一个人进来时，必须看见上一个人改完的结果（防「各看各的」）。

Java 官方把第二件事说得很明白：当一个线程释放锁，另一个线程随后拿到同一把锁，两者之间就建立了「**先发生**」关系，前面那位的修改对后面这位可见。

再把场景放大一层，就出现了第三种麻烦：

- 一个进程里的多个线程，共享同一块堆内存，门牌号互相认得；
- 一台机器上的多个进程，内存互相隔离，JVM 那把锁就管不着了；
- 几十台机器上的几百个进程，根本不认识彼此，更没有一块公共内存。

**会议室从「一间」变成了「全国分公司的一堆」**，白板挂在谁家？这就是分布式锁的来由。

> 一句话记住：**锁不是为了让程序变快，是为了让程序别乱。**

## 二、原理：锁凭什么能保证「只有一个人」

抛开各种语言的花哨名字，所有锁都是同一套动作，四步：

1. **申请**：想干活的人先去抢那个标记；
2. **占用**：抢到了就进屋，标记上写着自己的名字；
3. **排斥**：没抢到的人在门口等（专业说法叫**阻塞**），而不是一起挤进去；
4. **释放**：干完活把标记交还，门口的人才有机会进去。

Java 官方对这一步的描述非常精确：

> A thread that needs exclusive and consistent access to an object's fields has to acquire the object's intrinsic lock before accessing them, and then release the intrinsic lock when it's done with them. As long as a thread owns an intrinsic lock, no other thread can acquire the same lock. The other thread will block when it attempts to acquire the lock.

注意关键词：**「同一个标记」**。锁生效的前提是所有人都认同一个标记。两个人各拿一把自己的锁，等于没锁。这也是新手最常踩的坑：

```java
synchronized (new Object()) { ... }   // 每次进来都是新对象，锁了个寂寞
String lock = new String("order");     // 换个对象实例，两把锁互不相干
```

### 2.1 一个好锁要满足的三条底线

Redis 官方文档在讲分布式锁时，给出了三条「最低保证」，其实单机锁也一样适用：

| 底线 | 含义 | 会议室说法 |
|---|---|---|
| **互斥** | 任意时刻只有一个持有者 | 屋子里不能同时有两拨人 |
| **不死等** | 有人崩溃倒下，锁最终也能被别人拿到 | 钥匙不能跟着人一起锁进柜子里 |
| **容错** | 部分设施坏了，系统整体还能继续发锁/收锁 | 前台临时不在，也有备用登记方式 |

第二条在单机里靠「异常也释放」解决——Java 的同步块即使抛出未捕获异常也会释放锁，所以写 `try/finally` 是铁律。在分布式里靠**租约**（给锁设过期时间）解决：人晕倒了，钥匙过几分钟自动作废。

### 2.2 锁的两个「附加服务」

除了互斥，正经的锁还顺手提供两样东西：

- **可见性**：前面说的「先发生」关系，保证接力时看见正确结果；
- **可重入**：同一个线程已经拿着锁，再进一层用同一把锁，不会被自己卡死。Java 官方管这叫 reentrant synchronization——「允许一个线程多次获取它已经拥有的锁」。

顺带说一句：**锁的粒度**。锁太大（整个系统一把锁），所有人都排队，等于把并发废了；锁太小（每个字段一把锁），心智负担爆炸还容易漏。合适的粒度是「一次业务操作」：改订单就锁订单，别锁整栋楼。

### 2.3 悲观锁和乐观锁：两种性格

不是所有锁都靠「先把门堵上」。

- **悲观锁**：先占坑再干活，默认「肯定有人跟我抢」。`synchronized`、`ReentrantLock`、数据库的 `SELECT ... FOR UPDATE`、Redis 的 `SET NX` 都是这一类。
- **乐观锁**：不堵门，干活时记下版本，提交时检查「我看的时候到现在，有没有被人改过」。数据库版本号字段、CAS、Redis 的 `WATCH` 都是这一类。Redis 官方书里管 `WATCH` 叫**乐观锁**，因为它「并没有真的阻止别人改数据，而是在别人改了之后通知我」。

取舍很简单：**冲突多、改完代价大**用悲观；**冲突少、改起来很快**用乐观。

## 三、核心区别：单机锁 vs 分布式锁

终于到正题。先看一张对照表：

| | 单机锁 | 分布式锁 |
|---|---|---|
| 标记放在哪 | 进程内存里的一个对象头 / 操作系统内核 | Redis、数据库、ZooKeeper、etcd 等外部存储 |
| 谁在竞争 | 同一个进程里的线程（或同一台机器的进程） | 不同机器上的进程 |
| 怎么判断「谁拿着」 | 看对象头/互斥量里记的线程标识 | 看第三方存储里那条记录、值、过期时间 |
| 崩溃了怎么办 | 线程异常退出时释放；进程死了操作系统回收 | 必须设**租约**（过期时间），否则永久卡死 |
| 别人能不能偷看/误删 | 基本不能，地址空间隔离 | 能——任何人都能删那条 key，所以要校验值 |
| 性能 | 纳秒到微秒级，纯内存操作 | 毫秒级，多一次网络往返 |
| 典型实现 | `synchronized`、ReentrantLock、互斥量 | Redis `SET NX PX`、数据库唯一行、临时顺序节点 |

一句话总结区别：

> **单机锁靠「大家在同一块内存里看同一块牌子」，分布式锁靠「大家都在网上查同一本登记册」。**

### 3.1 最要命的误区：单机锁在集群里等于没锁

假设你写了个定时任务：

```java
@Scheduled(cron = "0 0 2 * * ?")
public void syncOrders() {
    synchronized (this) {
        doSync();
    }
}
```

本地跑得好好的。上线部署三台机器，凌晨两点**三台一起跑**，因为每台机器锁的都是自己内存里那个 `this`。

这就是单机锁和分布式锁的分水岭：**锁的作用域必须覆盖竞争者的范围**。竞争者跨进程跨机器，锁就必须放在所有人都能访问的地方。

### 3.2 分布式锁的正确打开方式（以 Redis 为例）

最基础的写法，Redis 官方给的是一条命令：

```
SET order:lock <随机值> NX PX 30000
```

- `NX`：key 不存在才设置——这就是「抢占标记」；
- `PX 30000`：30 秒后自动过期——这就是「租约」，防持有者崩溃后锁永不释放；
- `<随机值>`：**必须是全局唯一的随机串**，释放时校验。

释放不能直接用 `DEL`。官方特意强调了原因：客户端 A 加锁后卡顿超过 30 秒，锁过期被 B 抢走；这时 A 慢慢悠悠执行完，一个 `DEL` 就把**B 的锁**删了。所以要用 Lua 脚本（或新版 Redis 的 `DELEX`）做「**值匹配才删**」：

```
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

业务时间不可控时，还要有**看门狗**周期性续期。但看门狗不是万能的：进程真被长时间挂起（比如垃圾回收停顿），续期线程自己也停了。

### 3.3 主从切换那几毫秒，锁会丢

Redis 官方自己列了一个「四步翻车」序列，我照原意讲：

1. 客户端甲在主节点拿到锁；
2. 主节点宕机，锁还没同步到从节点（Redis 复制是**异步**的）；
3. 从节点被提升成新主节点；
4. 客户端乙向新主节点申请同一把锁，成功。**互斥被打破。**

官方的原话是 `SAFETY VIOLATION!`。 Redlock 算法（在多个互相独立的主节点上投票，超过半数且总耗时小于租约才算成功）就是想补这个洞。

### 3.4 连 Redlock 也有争议：栅栏令牌才是底牌

Martin Kleppmann 那篇著名的质疑指出：就算锁服务完美无缺，下面三件事依然能让两个人同时以为自己拿着锁：

- **进程停顿**：甲拿到锁后被挂起，租约到期、乙拿锁，甲醒来继续写；
- **时钟跳变**：某台机器的表往前跳，锁提前过期；
- **网络延迟**：甲的写请求在路上堵了一分钟才到存储服务，那时租约早没了。

他给的结论不是「换个更好的锁」，而是**让存储服务自己识别谁才是最新的**：

> 每次授予锁时返回一个**单调递增的令牌**，写请求必须带上它；存储服务记住见过的最大令牌，**拒绝任何比它小的写入**。

原文的例子：甲拿到令牌 33 后停顿，租约过期；乙拿到 34 并写入成功；甲醒来拿 33 去写，存储服务一看「34 都见过了」，直接拒绝。

Kleppmann 的关键判断是 Redlock「**没有生成栅栏令牌的机制**」，而且依赖过强的时序假设，所以他建议：只为效率用锁就用单实例；为正确性用锁就用有共识的系统（如 ZooKeeper、etcd 或带事务的数据库），并在资源访问处强制校验令牌。

这条结论对普通业务同样成立：**Redis 锁负责减少冲突，数据库约束负责兜底正确**。库存别只靠锁，还要有唯一约束或版本号。

## 四、什么时候需要锁：一张判断清单

先问自己三个问题：

1. **有没有共享状态？**（同一份数据、同一个文件、同一个外部资源）
2. **有没有多个执行者？**（多线程、多进程、多机器、多个定时实例）
3. **是不是「读—改—写」序列，且结果必须正确？**

三个都是「是」，才需要认真考虑锁。只要有一个「否」，多半不需要。

### 4.1 什么时候用单机锁

- 同一个进程里，多个线程改同一份堆内存对象；
- 单机多实例之间的文件、内存缓存写入；
- 临界区很短，纯内存操作，不涉及外部存储。

### 4.2 什么时候用分布式锁

- **定时任务只跑一个**：多实例部署的唯一调度；
- **防止重复提交/重复发券**：用户连点、消息重投；
- **多个节点争抢一个外部资源**：同一个文件、同一个账号的操作、同一批数据的批处理；
- **限流/配额的全局计数**（不过这一类用原子命令往往更好）。

### 4.3 什么时候不需要锁

- **没有共享**：无状态服务、每个请求只用自己的局部变量；
- **只读**：大家看同一份不变的数据，随便看；
- **不可变对象**：对象创建后就不改，天然线程安全；
- **线程隔离**：每个线程有自己的一份（如线程本地变量）；
- **一个原子操作就够**：Java 官方说，对引用变量和大多数基本类型的单次读写本身就是原子的；`volatile` 还能保证可见性。但官方也提醒：原子性不等于不需要同步——`c++` 是三步，不是一步；
- **数据库有更强约束**：唯一索引、版本号、事务已经能兜底，就别再套一层 Redis 锁。

Kleppmann 把用锁的目的分成两类，非常实用：

- **为了效率**：锁失败了只是多算一次、多写一封邮件。这种用简单方案就够，不必上复杂的锁集群；
- **为了正确性**：锁失败了就是数据错乱、超卖、重复扣款。这种必须清楚说明，并让存储层兜底。

### 4.4 七个常见坑

1. **锁对象换来换去**：每次 new 一个新对象当锁，等于没锁；
2. **忘记释放**：异常路径漏了 `finally`，锁永久占用；
3. **锁粒度太大**：整张表、整个方法一把锁，并发直接归零；
4. **锁过期但业务没干完**：租约时间拍脑袋定，必须留余量或续期；
5. **释放别人的锁**：不用随机值校验就 `DEL`；
6. **只看锁不看存储**：Redis 锁拿着，数据库却没有唯一约束；
7. **以为看门狗万能**：进程停顿、时钟跳变、网络延迟，它都救不了。

### 4.5 动手前六问

- 共享的是什么？说得出具体字段/文件/资源吗？
- 竞争者都有谁？线程、进程还是跨机器？
- 临界区里做了几步？能不能缩成一个原子操作？
- 崩溃时会怎样？锁能自动释放吗？
- 时钟/network 出问题时会怎样？存储层能识别旧持有者吗？
- 不用锁，用唯一约束 / 版本号 / 幂等能不能解决？

## 术语小抄

| 术语 | 大白话 |
|---|---|
| 临界区 | 同一时间只准一个人进的那段代码 |
| 互斥 | 有人在里面，外面的人就等着 |
| 竞态条件 | 结果取决于谁先谁后，而且顺序不受控 |
| 阻塞 | 抢不到锁就停在那等，不往下跑 |
| 管程 / 内部锁 | Java 里每个对象自带的那把锁 |
| 可重入 | 自己已经拿着锁，还能再用同一把进下一层 |
| 锁粒度 | 一把锁管多大范围 |
| 公平锁 | 先来先得；非公平锁允许插队，吞吐更高 |
| 悲观锁 | 先占坑再干活，默认有人抢 |
| 乐观锁 | 先干活，提交时查版本，发现被改就重试 |
| 原子操作 | 一步完成，中间不可被打断 |
| 可见性 | 一个人改完，下一个人看得见 |
| 租约 | 带过期时间的锁，防止持有者崩溃后永久占用 |
| 看门狗 | 后台线程周期性续租 |
| 栅栏令牌 | 单调递增的号码，存储层用它拒绝过期持有者 |
