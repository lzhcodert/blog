如果你用过 MySQL，可以把它想成楼下那家小卖部：老板一个人收钱、记账、发货，生意再好也只是把货架加高。GoldenDB 面对的是另一种场景——一个银行核心系统，数据量大到一台机器放不下，交易多到一台机器扛不住。办法不是把一台机器做得无限大，而是找一群机器分工，并让它们看起来仍然像「一台数据库」。

金篆信科在官方技术白皮书里的定义很直接：GoldenDB 是集中式与分布式一体化的数据库，整体由**计算节点、数据节点、全局事务管理器、管理节点**四种核心模块组成，采用 Share-Nothing 架构，各节点不共享资源，无单点故障。

## 一句话版本

**把一群普通机器伪装成一台数据库。** 应用还是照常写 SQL、连库表、开事务；后台已经把数据拆成多份，CN 负责派活，DN 负责真存真算，GTM 负责给跨机器的改动发号并判断谁生效。

## 先把四个角色认全

| 角色 | 官方说法 | 大白话 | 挂了会怎样 |
|---|---|---|---|
| CN 计算节点 | ComputeNode，无状态、对等；接 SQL、优化、路由、汇总 | 前台调度员：接单、看菜单、派给哪个厨房、最后拼菜 | 换一台 CN 继续服务，数据没事 |
| DN 数据节点 | DataNode，最终存储；按安全组做一主多备 | 仓库加账本：货真放在这里，正本和副本各一份 | 备节点顶上，继续读写 |
| GTM 全局事务管理器 | Global Transaction Manager；发 GTID、维护活跃事务和快照 | 发号员兼裁判：给每笔跨仓改动发唯一工单号 | 主备或集群切换，只影响绑定租户 |
| 管理节点 | Insight、元数据、监控、扩容、主备切换；不参与业务访问 | 物业或后台：装系统、看监控、调度资源 | 影响运维，不直接挡住业务 SQL |

这里最容易被误读的是 GTM：它**不存业务数据**，只管「谁在改、改到哪一步、这行改动算不算已经生效」。CN 也**不存业务数据**，所以才能无状态扩展。真正把数据落在磁盘上的，是 DN。

## 一条 SQL 在后台跑了几站

白皮书给的流向很清晰：应用连到 CN 的服务端口，CN 做语法解析和优化，生成分布式执行计划树，按连接实例定义把请求下发到对应数据节点子集群；DN 本地执行后把结果集返回，CN 再做汇总、排序、聚合，最后回给应用。中间可能有多次交互。

1. **建链**：应用连到 CN 的某个服务端口，这个端口绑定了后端哪组 DN。
2. **解析与优化**：CN 看懂 SQL，做逻辑优化和物理优化。
3. **路由**：根据分片规则判断数据在哪几个安全组，生成分布式计划树。
4. **本地执行**：DN 在自己这片数据上查或改，主节点负责写，备节点可以分摊读。
5. **汇总返回**：CN 把各片结果合并，业务侧看到的还是一张表、一条结果。

> 大白话：像点外卖。你只管下单，平台接单后决定哪个厨房做、要不要拆单，厨房出品后平台把几盒菜拼成一单送到你手上。你不需要知道后厨在哪条街。

## 数据怎么切：分片与安全组

一张大表不可能整块塞给一台 DN。GoldenDB 支持**哈希、范围、列表、复制、多级分片**：哈希适合均匀打散，范围适合按日期或数值分段，列表适合按地区、机构代码这类枚举值，复制适合不常改的小表，多级分片适合多法人这种精细场景。

切完之后，每一片会变成一个**安全组**：组里一个或多个 DN 持有相同数据，其中一个是主节点，其余是备节点，主备之间实时复制；副本使用改进的 raft 一致性协议同步，官方术语里还提到 gSync 同步复制技术。

还有两个细节很实用：

- **广播表**：不常改又经常被关联的小表，复制到每个分片，查询时不用跨节点找人；
- **全局索引**：用非分片字段查询时，先查到「这个字段对应哪条分片键」，避免把 SQL 群发到所有 DN。

## 它和 MySQL 到底哪里像

这是最值得说清楚的地方。官方白皮书的说法是：「兼容 MySQL 语法」「兼容 MySQL 的 sql_mode 特性，兼容 MySQL 的 binlog 特性」「分布式事务借鉴单机事务实现」。注意用词是**兼容与借鉴**，不是「把 MySQL 内核直接改成分布式」。

| 层面 | 相同的地方 | 大白话 |
|---|---|---|
| 接入 | 支持 JDBC、ODBC 等标准驱动与协议 | 原来的连接方式和客户端基本能沿用 |
| 写法 | 常用语法、数据类型、函数、自增列、存储过程、触发器、视图、sql_mode | 会写 MySQL，就容易上手 |
| 日志 | 兼容 binlog 特性；分布式回滚时 DBAgent 会解析 binlog 找 GTID | 还是用日志记录变更，也拿日志反推回滚 |
| 并发 | MVCC、undo 前像、读不加锁 | 读写不必互相排队 |
| 事务 | 四种隔离级别，推荐 Read Committed；ACID、XA 接口 | 还是「要么全做，要么全不做」 |

所以更准确的理解是：**它保留了 MySQL 的使用习惯和单机事务那套词汇，在集群层重新做了分片、路由、全局事务和可见性判断。**

多出来的那一层，恰恰是难点：CN 要会派活，DN 要会分片和复制，GTM 要发全局号并维护全局快照，每行还要多一个 GTID 隐藏列。

## 跨分片转账：最难的那一题

假设 A、B 两个账户在不同分片，A 给 B 转 50 元。最大的风险是：A 扣成功了，B 加失败了，钱凭空消失。

白皮书给出的做法是：

1. CN 向 GTM 申请一个全局唯一且递增的事务 ID，也就是 **GTID**；为了少跑腿，官方还做了批量申请和批量释放；
2. GoldenDB 给所有表增加一个 **GTID 隐含列**，更新数据时同步更新它，把它当作分布式环境下的「全局锁」；
3. CN 作为协调者，用改进的两阶段提交协调多个 DN 上的本地事务；所有 SQL 执行完后，各 DN 统一提交；
4. 如果某个 DN 提交失败，其他节点上的 DBAgent 会解析 binlog，找出带有这个 GTID 的改动，构造反向 SQL 下发回滚。

> 大白话：两个仓库同时搬货，总部给这次搬运发同一张运单号 9527。其中一个仓库搬砸了，就按运单号把另一个仓库已经搬走的货原样搬回来。于是不会出现「钱扣了、没到账」。

这就是官方文档强调的**强一致**：更新完成后，后续读操作只能读到更新后的值。

## MVCC：读为什么不用等写

单机 MySQL 里，MVCC 让读不加锁、读写不冲突；GoldenDB 要做的是「分布式 MVCC」。

白皮书描述的过程是：SELECT 发起时，CN 拿到一份全局活跃事务列表 `active_gtm_gtid_list`，并把它带到 DN 做可见性判断。

- 数据行上的 GTID **不在**活跃列表里：说明这批改动已经全局可见，直接返回当前数据；
- 数据行上的 GTID **在**活跃列表里：说明改它的人还没尘埃落定，就通过 undo 构造前像数据，继续往前找，直到找到全局可见的版本。

> 类比：你读一本正在被修改的账簿。每改一次就贴一张旧页备份。管理员告诉你「101 号修改还没盖章」，你就跳过它，看上一版已经盖章生效的账页。

这里的差别在于：单机看的是本地活跃事务，GoldenDB 还要把 GTM 的全局名单带下来。这是「分布式」三个字真正贵的地方。

## 什么时候值得上分布式

官方给了三种部署形态：

- **集中式**：单分片租户，不带 GTM，只有普通事务；适合数据量不大、不用分片的情况；
- **分布式**：多分片租户，带 GTM；数据跨片、事务跨片，才需要全局事务管理；
- **混合**：同一个集群里同时有单分片和多分片租户，并且可以在集中式和分布式之间在线转化。

所以别把分布式当银弹。数据量小、单机扛得住时，简单就是优势；当单机容量和性能真的成为瓶颈，再让 CN、DN、GTM 这套分工上场。

CN 管去哪查，DN 管真存真算，GTM 管跨机器算不算数；和 MySQL 像在写法和单机事务，难在把这套写法搬到一群机器上还不出错。
