先看一组真实数字。

Gartner 的数据说，2024 年全球 CRM 软件市场规模约 **1280 亿美元**，同比增长 **13.4%**，是它跟踪的最大软件品类。IDC 的口径小一些，按 Salesforce 的收入反推约 1040 亿美元——两个数字都对，差别只在「CRM」这个圈画多大。Salesforce 一家就占了全球约 20% 的份额，Microsoft、SAP、Oracle 紧随其后。

但国内市场有个尴尬现象：买了 CRM 却用不起来。有制造企业花一年选型、八个月上线，最后系统里只有财务导入的历史名单和月末补录的拜访记录。销售总监的原话是：「系统最大的作用是让我知道谁在裸奔。」

**功能都买齐了，为什么还是用不起来？** 多数时候不是功能不够，而是架构没搭对：流程没理顺就先定制字段，数据没有主数据就先上画像，多个系统各存一份客户就指望报表能对上。

这篇就用之前讲过的**四种架构**（业务 / 应用 / 数据 / 技术），把一套规范的 CRM 拆开看。还是那句话：这四层不是四份 PPT，是同一个系统的四种画法。看完你应该能回答——「我们这个 CRM 问题，到底该在哪一层解」。

> 说明：文中的连锁企业、门店与团队规模是为讲解构造的示例；市场规模与厂商份额来自 Gartner / IDC 口径，厂商自身的排行榜有立场，只作背景参考。

## 先说市场：CRM 早就不是「一个销售通讯录」

理解架构之前，先看清楚这门生意现在卖的是什么。

分析机构对「CRM」的定义早已超出「管客户联系方式」。它是一捆软件：销售自动化、营销自动化、客户服务与支持、电商，外加把这些数据串起来的平台。Salesforce 官方把 CRM 按用途分成三类：

| 类型 | 干什么 | 大白话 |
|---|---|---|
| 操作型（Operational） | 自动化面向客户的流程：销售、营销、服务 | 让一线干活有章法，别漏跟进 |
| 分析型（Analytical） | 分析客户数据、挖掘洞察、预测趋势 | 让后台看清谁值得跟进、谁要流失 |
| 协作型（Collaborative） | 打通内部团队与外部伙伴的沟通渠道 | 让销售、客服、渠道看到同一个客户 |

还有厂商加第四类「策略型」，意思是把客户放到公司战略中心。**三类就够了**：一类管「干」，一类管「看」，一类管「一起干」。

市场也在变。最近两年所有大厂都在卖 AI 坐席和智能体：Salesforce 的 Agentforce、微软的 Copilot，定价从「按人头」变成「按对话次数 / 按结果」。国内厂商则更强调信创、私有化和复杂组织架构。

**这就是架构要面对的现实**：你买的不是一个工具，是一个要同时接住流程、数据、渠道、AI 和合规的平台。只画一张功能清单，根本接不住。

## 第一层：业务架构——先把「客户关系」这门生意讲清楚

业务架构不谈系统。它只回答三件事：**给谁提供什么价值、靠哪些能力、按什么顺序串**。

还是用一家连锁企业举例（虚构，但流程是真实的）：线上留资 → 线索分配 → 跟进转化 → 签约开卡 → 到店消费 → 售后服务 → 复购推荐。这是价值链，是客户视角。

公司视角要画能力地图：获客能力、线索能力、销售能力、会员能力、服务能力、分析能力。**价值链上每一环，都要有对应能力托住**。如果「复购推荐」这一环没人负责，那不是技术债，是业务设计缺口。

CRM 业务架构里最容易被漏掉、最值钱的是**业务规则**：

- 一条线索多久没跟进就回收？回收给谁？
- 一个客户归销售还是归客服？冲突时谁说了算？
- 会员积分按消费额还是按次数？退货怎么扣？
- 客户信息能不能导出？谁审批？留痕多久？
- 营销触达一天最多几次？客户投诉后是否自动停推？

这些规则写不清，后面三层全是猜。开发按自己理解实现，上线就是「系统跟业务说的不一样」——这正是不少企业「买了不用」的根因：一线觉得系统不合实际，只好线下另记一份。

**常见画错**：把业务架构画成部门组织架构图。部门会重组，能力不会。能力地图描述「公司得会做什么」，部门只是当下的责任人。

## 第二层：应用架构——功能放在哪个系统里

业务说清了要做哪些事，应用架构负责把这些事分配到具体系统，并规定怎么调用。核心词只有一个：**边界**。

一套规范 CRM 的应用层，通常长这样（见文末图 3）：

- **触点层**：官网、App、小程序、企微、门店终端、呼叫中心。它们只负责采集和展示，不存业务主数据。
- **业务应用层**：线索管理、客户管理、商机与销售漏斗、营销活动、工单与服务、会员与权益。这是操作型 CRM 的主战场。
- **分析应用层**：客户画像、标签体系、流失预警、营销效果归因。这是分析型 CRM，数据来自数据层，不直接改业务库。
- **协同应用层**：渠道门户、内部知识库、消息中心。这是协作型 CRM，把销售、客服、经销商拉到同一张桌上。
- **平台能力**：流程引擎、规则引擎、权限与审批、消息总线、开放 API。

判断边界好不好，还是那三条土办法：

1. **一份数据只有一个系统能改。** 客户主数据只在客户中心改，营销系统只能引用，不能自己存一份手机号。
2. **一个模块挂了别家还能用。** 画像服务挂了，销售还能录商机，只是看不到推荐。
3. **换一个实现不用改别人代码。** 换一家短信服务商，不该动五个系统。

这里要结合市场现实做一个取舍：**买套件还是自己拼**。

Salesforce、Microsoft Dynamics 365、SAP 给的是套件，模块天生打通，贵且定制受限；国内厂商更擅长复杂审批、多组织与信创适配。自己拼的好处是灵活，代价是接口、权限、口径全要自己维护。多数企业的正解是「**套件为主、关键能力自建**」：核心交易与客户主数据放在一个平台，画像、推荐这类分析能力可以外接。

顺带说清楚单体和微服务：**CRM 不必一上来就微服务**。三五个人、业务还在试错，一个边界清楚的单体比强行拆十个服务健康。什么时候拆？看三件事——团队能否独立发布、某块功能是否要独立扩容、故障是否需要隔离。三条都不需要，就别拆。

## 第三层：数据架构——客户只有一份，口径只有一套

很多人以为 CRM 的数据架构就是画客户表。真正的难点有三件：**数据从哪来、怎么加工、口径谁说了算**。

一条完整的数据旅程分四段（见文末图 4）：

- **源系统**： CRM 自身的交易数据，加上 ERP 的订单、财务的回款、App 的行为埋点、呼叫中心的录音转写。这里是数据的出生地。
- **贴源层 ODS**：原样同步，不加工。作用是出事能回溯到原始数据。
- **明细层 DWD**：清洗、去重、统一字段。作用是让全公司认同一套「一个客户」是什么。
- **画像 / 标签 / 集市**：按主题组装成宽表，让画像和营销跑得快。

这条链上最容易出事的不是存储，是**口径**。

同一个「活跃客户」，运营说是「七天内有登录」，销售说是「七天内有跟进」，财务说是「七天内有付款」。三个数都对，放在同一场会上就是吵架。所以数据架构真正要产出的，除了表结构，还有三样东西：

- **客户主数据**：客户 ID 全公司唯一，手机号、客户等级、归属人只在一处维护。口径打架的根因，八成是主数据有多份。
- **指标口径**：每个指标一句话定义 + 一个负责人。定义要写到别人能复算出来。
- **数据流与生命周期**：哪些实时同步、哪些 T+1 批量、存多久、谁能看、能不能导出。

还有一个必须分清的界限：左边那堆源系统是 **OLTP**（交易，一行一条，要快要准），右边的加工是 **OLAP**（分析，一批一堆，要全要能算）。两件事混在一个库里做，白天报表一跑，销售录入就开始卡。这也是为什么规范的 CRM 会把分析读数引到读库或数据集市，而不是直连交易库。

对金融、政企这类强监管行业，还要加一条：**数据不出域、访问留痕、脱敏可配置**。客户信息不是普通业务数据，合规不是上线后再补的功能。

## 第四层：技术架构——到底跑在什么上面

前三层说「做什么」，技术架构说「用什么、部署在哪、怎么扩、坏了怎么办」。

它最容易被当成全部架构，其实只是最底下那层。规范画法通常是五层（见文末图 5）：

- **接入层**：网关、负载均衡、WAF、移动端与开放 API。
- **应用运行层**：容器与编排、或虚机、或 Serverless。
- **中间件层**：消息队列、缓存、流程引擎、分布式任务、统一认证。
- **数据存储层**：关系库存交易、对象存储放录音和附件、搜索引擎做检索、数仓与数据集市做分析。
- **基础设施层**：公有云、私有云或信创环境，网络、备份、容灾。

外加两条贯穿所有层的公共能力：**可观测**（日志、指标、链路、告警值班）和**安全**（认证授权、传输加密、密钥管理、审计留痕）。它们不是一个层，是每层都要有。

市场现实让这一层多了三个必答题：

1. **公有云还是私有化？** 大厂 SaaS 迭代快但数据在外；国内政企、金融客户常要求私有化或信创适配。选型前先确认合规红线在哪。
2. **出问题怎么恢复？** RTO（多久恢复）、RPO（能丢多少数据）要写进合同，不是写在 PPT 里。
3. **涨到十倍怎么办？** 客户量翻十倍、坐席翻十倍，扩容路径和成本要能算清楚。

答不上第三题的选型，通常上线半年后开始还债。

## 同一个需求，四层各改什么

光看图容易觉得「四种架构」是四份文档。真正的价值在改需求的时候。

假设业务说：**要给高价值客户做「智能复购提醒」，系统自动挑人、自动推送、还能看效果。**

| 层 | 要改什么 | 连锁问题 |
|---|---|---|
| 业务架构 | 价值链在「售后」与「复购」之间加一环；定义什么叫高价值、谁审批触达、客户投诉后如何停推 | 运营和销售谁负责？触达频次规则谁定？ |
| 应用架构 | 选品与推荐放画像服务还是营销服务？消息中心要不要新增渠道？权限怎么隔离 | 画像服务挂了，营销还能不能跑？ |
| 数据架构 | 新增「复购倾向」指标与口径；标签回写路径；效果归因的口径一次定清 | 历史数据要不要补？归因窗口多少天？ |
| 技术架构 | 实时打分的算力与延迟；消息洪峰的削峰；推送失败的重试与告警 | 要不要上流计算？第三方通道挂了怎么降级？ |

**业务规则一变，下面三层全跟着动。** 这就是为什么「先定业务架构」不是流程洁癖。

## 四种最常见的画错方式

1. **只画功能清单，叫它「架构」。** 老板看不到流程、数据没人对口径，最后只剩一张采购清单。
2. **业务架构画成部门图。** 部门会重组，能力不会。
3. **数据架构只画 ER 图。** 表结构之上要补数据流、主数据和指标口径，否则交付时才发现三个报表三个数。
4. **把技术栈图当整体架构。** 应用图讲边界与调用，部署细节归技术层，各画各的。

交图前问自己三句：

- 这张图回答的是「做什么 / 放哪里 / 数据怎么流 / 跑在哪」里的哪一个？
- 看完能指出责任人吗？
- 改一处，图上有几处要跟着改？

## 小团队怎么开始

不必一上来就画四张精图。一页纸就够：

- **业务格**：客户从哪来、怎么成交、靠什么本事留住。
- **应用格**：这些本事现在由哪个系统承担，哪些还没人管。
- **数据格**：客户主数据是谁、核心指标怎么定义、哪些数据要实时。
- **技术格**：现有栈、团队会什么、合规红线在哪。

四格填不满的地方，通常就是项目后面要出问题的地方。架构图不是用来汇报的，是用来提前发现「这里还没想清楚」的。

## 术语小抄

| 术语 | 大白话 |
|---|---|
| 业务架构 | 这门生意怎么做，靠哪些能力 |
| 应用架构 | 功能放哪个系统，系统之间怎么调用 |
| 数据架构 | 数据从哪来、怎么流、口径谁说了算 |
| 技术架构 | 跑在什么上、怎么扩、坏了怎么办 |
| BDAT | TOGAF 的四个架构域：业务、数据、应用、技术 |
| 操作型 CRM | 让一线把活干规范的那一套 |
| 分析型 CRM | 让后台看清客户、预测趋势的那一套 |
| 协作型 CRM | 让销售、客服、渠道看到同一个客户的那一套 |
| SFA | 销售自动化：线索、商机、跟进、预测 |
| 客户主数据 | 全公司唯一的那份客户档案 |
| 数据集市 | 按主题加工好、即取即用的宽表与标签 |
| ODS / DWD | 贴源层 / 明细层：原样同步 / 清洗去重 |
| OLTP / OLAP | 交易处理 / 分析处理，一个要快要准，一个要全能算 |
| RTO / RPO | 多久能恢复 / 能容忍丢多少数据 |
