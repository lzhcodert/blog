一句话说清：**死锁就是几个人各占着一件别人要用的东西，又都等着别人先松手，结果谁也不动。**

它不像空指针那样啪一下报错，而是程序"看起来还在跑"，实际上线程全卡住、日志不再增长、请求一直不返回。更烦的是，重启就好了，于是很多人把它当玄学。其实它是有确定形状的：一个环。

## 死锁到底是什么

经典定义是：两个或两个以上的线程在执行过程中，因为竞争资源或彼此通信而互相等待，没有外力就都无法推进。

放到 Java 里，最常见的画面是：

```text
A线程：拿着 object1，想拿 object2（在 B 手里）
B线程：拿着 object2，想拿 object1（在 A 手里）

        ┌──────── 等待 object2 ────────┐
        │                              ▼
      A线程                          B线程
        ▲                              │
        └──────── 等待 object1 ────────┘
```

只要这个环闭上，两个线程就会永远停在 `synchronized` 门口。

## 四个条件：必须同时成立

死锁有四个必要条件，缺一个都死不了。理解它们，比背定义有用得多。

| 条件 | 大白话 | 能不能破 |
|---|---|---|
| 互斥使用 | 一把锁同一时刻只给一个人 | 基本不能破，锁本来就是干这个的 |
| 不可剥夺 | 别人手里的锁，你抢不走，只能等他主动放 | 可以破：`tryLock` 超时后自己退让 |
| 请求和保持 | 手里拿着一把，还去要另一把，而且不放手里这把 | 可以破：一次性申请全部，或申请不到就先放 |
| 循环等待 | A 等 B、B 等 C、C 又等 A，首尾接上 | 最好破：所有线程按同一顺序加锁 |

注意最后一句话：**四个条件同时满足才会死锁**。所以"避免死锁"不需要四个全改，拆掉后面三个里的任意一个就够了。

## 用一段代码把它复现出来

下面这段代码来自韩顺平教程的死锁模拟，原文里就有，这里做了排版整理，并加了一个 100 ms 的 `sleep`——不是为了制造 bug，而是为了让"各拿一把"的窗口稳定出现，跑一次就能看到死锁。

```java
/**
 * 模拟死锁：两个线程各持一把锁，再互相申请对方手里的锁。
 */
public class DeadLock {
    public static void main(String[] args) {
        ThreadDemo a = new ThreadDemo(true);
        ThreadDemo b = new ThreadDemo(false);
        a.setName("A线程");
        b.setName("B线程");
        a.start();
        b.start();
    }
}

class ThreadDemo extends Thread {
    // static 很关键：无论 new 多少个 ThreadDemo，看到的都是同一两把锁
    private static final Object object1 = new Object();
    private static final Object object2 = new Object();

    private final boolean flag;

    public ThreadDemo(boolean flag) {
        this.flag = flag;
    }

    @Override
    public void run() {
        if (flag) {
            synchronized (object1) {
                System.out.println(Thread.currentThread().getName() + "---开始持有资源object1");
                sleepABit();
                synchronized (object2) {
                    System.out.println("第一个线程拿到object2");
                }
            }
        } else {
            synchronized (object2) {
                System.out.println(Thread.currentThread().getName() + "---开始持有资源object2");
                sleepABit();
                synchronized (object1) {
                    System.out.println("第二个线程拿到object1");
                }
            }
        }
    }

    private static void sleepABit() {
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

典型输出只有两行，然后就安静了：

```text
A线程---开始持有资源object1
B线程---开始持有资源object2
```

程序没退出，也没异常。因为它没有"出错"，只是两个线程都在等一把永远拿不到的锁。

### 这段代码里藏着三个关键点

1. **`static` 让锁变成共享的。** 如果写成普通成员变量，每个 `ThreadDemo` 实例都有自己的 `object1/object2`，那两把锁根本不冲突，死锁演示不出来。
2. **嵌套 `synchronized` 就是"请求和保持"。** 进入外层 `synchronized` 后锁没放，又去申请内层锁，正好踩中第三个条件。
3. **两个线程的加锁顺序相反。** A 是 `object1 → object2`，B 是 `object2 → object1`，环就来自这里。

## 怎么确认它是死锁，而不是单纯卡住

"卡住"不等于"死锁"。可能是慢 SQL、网络等超时、线程池队列满，也可能真是死锁。别猜，抓线程栈。

### 第一步：找到进程

```bash
jps -l
```

输出类似：

```text
107840 DeadLock
99504
110052 KotlinCompileDaemon
113212 Jps
```

记下 `DeadLock` 前面的 PID：`107840`。

### 第二步：抓栈

```bash
jstack -l 107840
```

`-l` 会额外打印关于可持有同步器的信息。真正的死锁，JVM 会主动帮你检测并在末尾给出一段：

```text
Found one Java-level deadlock:
=============================
"B线程":
  waiting to lock monitor 0x00007f..., (object 0x000000076cda86f8, a java.lang.Object),
  which is held by "A线程"
"A线程":
  waiting to lock monitor 0x00007f..., (object 0x000000076cda8708, a java.lang.Object),
  which is held by "B线程"
```

比原文里更直接的读法：

- `waiting to lock <地址>`：这个线程正在门口等哪把锁；
- `locked <地址>`：这个线程手里已经拿着哪把锁；
- 把"谁拿着"和"谁在等"配对，就能画出上面那个环。

线程状态也有讲究。`synchronized` 抢锁失败通常是 `BLOCKED`；`LockSupport.park()` 或 `Object.wait()` 则显示为 `WAITING / TIMED_WAITING`。死锁两种状态都可能出现，所以看栈里的锁地址比只看状态更靠谱。

### 第三步：图形界面兜底

不想敲命令，可以 `Win + R` 输入 `jconsole`，连到目标进程，切到"线程"标签，点"检测死锁"。它会直接列出互相持有的两个线程，和 `jstack` 结论一致。

### 现场排查四步法

1. **看现象**：请求不返回、日志停住、线程数只增不减、CPU 反而很低。
2. **抓现场**：`jps -l` 找 PID，`jstack -l <pid>` 导栈；线上建议连抓三次，间隔 5 秒，避免单次采样误判。
3. **配对锁地址**：找 `waiting to lock` 和 `locked` 的同一串十六进制地址，连成等待链；链闭合成环就是死锁。
4. **先救火再治本**：救火靠重启 / 摘流量；治本靠下面的拆环办法。

## 怎么拆：四种办法，从最推荐到最省事

### 1. 统一加锁顺序（首选，破坏循环等待）

既然环来自"顺序相反"，那就让所有线程按同一顺序加锁。改原文代码，去掉 `flag` 分支即可：

```java
@Override
public void run() {
    // 所有线程都先 object1，再 object2
    synchronized (object1) {
        System.out.println(Thread.currentThread().getName() + "---开始持有资源object1");
        sleepABit();
        synchronized (object2) {
            System.out.println(Thread.currentThread().getName() + "---拿到object2，继续干活");
        }
    }
}
```

这样 B 想进 `object2` 之前，必须先拿到 `object1`；拿不到就在第一把锁门口等，绝不会出现"A 拿 1 等 2、B 拿 2 等 1"的交叉。

业务上确实没法写死顺序时，可以给资源编号（比如按数据库主键、按对象 ID），一律先小后大。**别用 `identityHashCode()` 当顺序**，哈希碰撞时一样会死锁。

### 2. tryLock 超时（破坏请求和保持）

`synchronized` 拿不到锁就死等，没法反悔。换成 `ReentrantLock.tryLock(timeout)`，第二把锁拿不到就把第一把也放了，环就接不上。

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class SafeTransfer {
    private static final Lock lockA = new ReentrantLock();
    private static final Lock lockB = new ReentrantLock();

    public void transfer(boolean first) {
        Lock firstLock = first ? lockA : lockB;
        Lock secondLock = first ? lockB : lockA;

        boolean gotFirst = false;
        boolean gotSecond = false;
        try {
            gotFirst = firstLock.tryLock(1, TimeUnit.SECONDS);
            if (!gotFirst) {
                System.out.println("第一把锁没拿到，直接放弃");
                return;
            }

            gotSecond = secondLock.tryLock(1, TimeUnit.SECONDS);
            if (!gotSecond) {
                System.out.println("第二把锁超时，准备放掉第一把");
                return;
            }

            // 两把都拿到了，安全地干活
            System.out.println(Thread.currentThread().getName() + " 完成转账");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            // 关键：拿不到第二把时，第一把也必须在 finally 里释放
            if (gotSecond) secondLock.unlock();
            if (gotFirst) firstLock.unlock();
        }
    }
}
```

注意 `finally` 里的两行：这才是真正"拆环"的地方。只在成功分支解锁，超时那次就会把第一把锁攥到天荒地老，等于没改。

### 3. 一次性申请所有资源

为每个业务操作提前列出需要的全部锁，一次性申请；只要有一个拿不到，就整体放弃并全部释放。银行家算法就是这个思路。优点是彻底，缺点是资源粒度和业务耦合重，Java 业务里不如前两种常用。

### 4. 缩小锁范围，别套娃

很多时候死锁不是因为"必须用两把锁"，而是把锁范围写大了：一个 `synchronized` 里调用了别的 `synchronized` 方法，又因为回调绕回了原锁。能拆成"各锁各的数据"就别用大锁；能用 `ConcurrentHashMap`、`AtomicInteger` 这类线程安全工具，就别自己套锁。

## 三个常见误区

- **"加了 `volatile` 就不会死锁。"** 不会。`volatile` 只保证可见性和禁止重排序，不提供互斥，也不解决锁的持有等待。
- **"把 `synchronized` 换成 `Lock` 就没事。"** 不会。`lock()` 一样是死等，照样能死锁；只有 `tryLock()` 才给了你反悔的机会。
- **"死锁一定会让 CPU 飙高。"** 通常相反。线程都在 `BLOCKED`，不消耗 CPU，所以"CPU 很闲但请求不回"反而该怀疑死锁。

## 小结

把这篇文章压缩成四句话：

1. 死锁 = 持有 + 等待 + 不成环才怪；
2. 四个条件同时成立才死锁，互斥别动，拆后三个；
3. 排查靠 `jps` + `jstack -l`，看 `waiting to lock` 和 `locked` 配成环；
4. 修复首选**统一加锁顺序**，需要反悔能力就用 **`tryLock` 超时 + 全量释放**。
