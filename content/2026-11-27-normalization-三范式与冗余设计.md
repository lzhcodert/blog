最近重读了一篇 2022 年的面试笔记《数据库三范式》，它的总结是三句话：

> 第一范式：每个列不可再分
> 第二范式：每个列都依赖于主键列
> 第三范式：每个列不可依赖于除了主键列的其它列

这三句好记，但后两句**少说了关键限定词**，照着字面理解很容易把错的设计当成合规。这篇就用一张订单表把三级范式串起来，再专门回答一个更实用的问题：**什么时候必须守范式，什么时候该故意留冗余。**

## 先说三个词：主键、依赖、冗余

范式全是在讲"列和列之间的依赖关系"，所以先把三个词说人话：

| 词 | 大白话 |
|---|---|
| 主键 | 能唯一确定一行的字段，相当于身份证号。可以是一列，也可以是几列合起来（联合主键，两把钥匙一起开锁） |
| 依赖 | 知道 A 的值，就能唯一算出 B 的值，就叫 B 依赖于 A。比如知道出生日期能算出年龄 |
| 冗余 | 同一份事实存在多个地方。客户名既在客户表、又在订单表，就是冗余 |

范式做的事，就是**规定一份事实只能有一个落脚点**。这样改的时候只改一处，不会漏。

## 第一范式：每个列不可再分

大白话：**一个格子只放一个值。**

原文的例子是"姓名 | 计科1909"，"计科1909"里挤着专业和班级两个数。以后想统计"计科有多少人"，数据库没法直接比，只能做字符串截取。拆成"专业=计科、班级=1909"，想查谁查谁。

放到订单表上，问题长这样：

```sql
-- 违反 1NF：一格塞了两个能独立使用的信息
订单号 | 客户信息
1001   | 张三 / 13800000000
```

```sql
-- 满足 1NF：拆成两列
订单号 | 客户姓名 | 客户电话
1001   | 张三     | 13800000000
```

**关键补充**：原文自己也说了"存在主观性"——拆不拆取决于业务要不要单独用这个值。如果"计科1909"永远只当一整串展示，从不按专业或班级统计，那它就可以是一列。微软官方文档的表述也是"消除单个表中的重复组"、"不要在单个表中使用多个字段来存储相似的数据"（见出处 1、3）。

所以 1NF 的判断口诀是：**这一列以后还要不要拆开单独查？要，就还没到 1NF。**

## 第二范式：每个列都依赖于主键列（少说了两个字）

准确说法是：**每个非主键列都要完全依赖于整个主键。**

少了"完全"和"整个"，就会把错误设计当成合规。因为"只依赖主键的一部分"也算"依赖于主键"，但它恰恰是 2NF 要禁止的。

原文的**成绩表**是正面例子：主键是（学号, 课程号），成绩必须两列合起来才能确定——单独学号不知道是哪门课，单独课程号不知道是谁考的。这叫"完全依赖"，合规。

原文的**比赛表**是反面例子：主键是（球员编号, 比赛编号），但"姓名、年龄"只看球员编号就够了，"比赛时间、场地"只看比赛编号就够了。每列只依赖了主键的一半，叫**部分依赖**，违反 2NF。

违反 2NF 会出四类事，原文列得很清楚：

- **数据冗余**：同一个球员姓名、同一场比赛时间重复存很多遍
- **插入异常**：新增一场比赛但还没定球员，整行插不进去（主键缺一半）
- **删除异常**：删掉某球员，连带把比赛信息一起删掉
- **更新异常**：比赛改时间，要改所有相关行，漏一行就出现"一场比赛两个时间"

微软官方文档给的也是同一个例子：ProductColor 表用（ProductID, Color）做联合主键，却把 Price 放进来——价格只依赖 ProductID，于是同一个产品的价格重复三行，改价时容易漏（见出处 2）。

**修法不是删字段，而是搬字段**：把只依赖部分的列搬到它真正的主人那里。原文的比赛表拆成三张：球员表（球员编号、姓名、年龄）、比赛表（比赛编号、时间、场地）、球员比赛表（球员编号、比赛编号、得分）。

## 第三范式：每个列不可依赖于除了主键列的其它列（也说反了主语）

准确说法是：**非主键列之间不能有依赖，不能出现 A → B → C 的传递依赖。**

原句说"每个列不可依赖其它列"会把主键自己也圈进去，但主键正是依赖的起点，逻辑上讲不通。要约束的对象是**非主键列**。

原文的员工表例子：

```
员工编号 → 部门编号 → 部门名称、部门简介
```

员工编号是主键，部门编号直接依赖它，没问题。但部门名称和简介其实**是通过部门编号中转**得到的，不是员工编号直接决定的，这叫**传递依赖**，违反 3NF。

大白话：销售部改名，员工表里几千行都得跟着改；拆出部门表后只改部门表那一行。合规设计是员工表只留"员工编号、姓名、部门编号"，部门信息放部门表。

微软官方给的例子同构：ShortLocation（国家简称）依赖 ProductionCountry，而 ProductionCountry 不是主键，所以 ProductInfo 表在 2NF 但不在 3NF（见出处 2）。

## 三句话的正确版本

| 范式 | 常见口诀 | 严谨版 | 治的病 |
|---|---|---|---|
| 1NF | 每个列不可再分 | 按业务需要，一列不要包含多个能独立使用的值 | 复合格子没法查、没法改 |
| 2NF | 每个列都依赖于主键列 | 每个非主键列**完全依赖整个主键**，不能只依赖联合主键的一部分 | 冗余、插入/删除/更新异常 |
| 3NF | 每个列不可依赖于其它列 | **非主键列之间**不能有依赖，不能传递依赖 | 同一事实散落多处，改起来漏 |

一句话记忆：**1NF 管一格，2NF 管一把钥匙，3NF 管别绕弯路。**

## 什么时候必须使用三范式

这里有个官方口径可以直接引用：微软 Learn 明确写着 **"Third normal form is typically the aim for most OLTP databases"（第三范式通常是大多数 OLTP 数据库的目标）**（见出处 2）。所以默认答案很明确：**交易型系统，做到 3NF。**

具体命中下面任意几条，就老老实实守：

1. **核心交易表**：订单、支付、账户、库存、客户资料。这类表写多读也多，最怕的是"改一处漏一处"。
2. **同一事实会被多处修改**：客户改名、部门改名、商品改价。只要一个事实有两个落脚点，就一定会有一处没同步。
3. **频繁插入、删除**：违反 2NF 的表容易出现"新比赛没球员就插不进去"、"删球员把比赛删了"这类业务上完全说不通的异常。
4. **强一致和审计要求**：金融账务、库存扣减，必须"同一时刻只有一个正确答案"，异步同步的窗口期不可接受。
5. **读写都频繁，冗余同步成本高**：冗余字段每次写都要跟着更新，写多的时候反而把范式省下的联表成本又赔进去了。
6. **数据量还不大，联表代价可控**：这时候为了"性能"提前拍平，属于过早优化。

微软还有一句很实在的提醒：**如果决定违反前三个范式中的任何一条，要确保应用程序能预见重复数据和不一致依赖带来的问题**（见出处 1）。换句话说，守范式是默认选项，破范式要付代价。

## 什么时候需要冗余设计

官方同样给了反向口径：**"规范化数据经常需要多次联表才能取齐所需数据；非规范化数据联表更少、CPU 更低，但打开了更新异常的口子。非规范化对读密集型负载（如数据仓库）更高效"**（见出处 2、6）。

命中下面几条，就该考虑故意冗余：

1. **读远多于写**：报表、看板、后台列表页、商品详情聚合页。写一次读一万次，把联表成本摊到每次读上非常亏。
2. **联表真的把 CPU 打满了**：注意是"真的"，要有慢查询和 CPU 数据支撑，不是"感觉 join 有点慢"。
3. **分库分表后跨库 join 做不到或代价极高**：这是分布式数据库里最常见的冗余理由。订单在一个库、客户在另一个库，跨库联表要么不支持，要么把两个库都拖慢。
4. **统计值实时算太贵**：订单总额、点赞数、库存可用数。每次 `COUNT(*)` 扫大表不现实，就冗余一个计数字段，写的时候维护。
5. **需要历史快照**：下单时的商品价格、客户姓名。这类字段不是冗余，是业务事实（下面单独讲）。
6. **字段几乎不变**：地区码、性别、证件类型。冗余了也很少需要同步，风险低。

微软 Azure 架构指南也给了同样的分工：**OLTP 系统通常用规范化模式做高效事务处理，OLAP 系统可能用非规范化结构或数据仓库技术优化查询性能**（见出处 7）。数据仓库的星型模型本质就是"事实表 + 宽维表"的冗余设计；雪花模型把维表再规范化，省空间但查询要多联表——这正是同一组取舍的另一面。

## 冗余的四个护栏

决定冗余之后，工作量才开始。少一样，线上就多一类脏数据：

1. **定主表**：每个冗余字段写清楚"以哪张表为准"。没有主表的冗余，出错后连"谁对谁错"都判断不了。
2. **定路径**：源表变更时怎么同步？同一个事务里更新，还是靠消息异步更新？异步就要接受短暂不一致。
3. **定时校对**：跑差异脚本，定期比源表和冗余列，发现不一致立刻修。没有校对的冗余，等于把一致性问题推迟到线上爆。
4. **只冗余读多写少、几乎不变的字段**：把"经常改、又要求实时准确"的字段冗余出来，等于主动制造更新异常。

微软中文文档的建议更保守：**只对经常变动的数据套用第三范式，其余依赖字段则设计应用程序，在更改相关字段时要求用户验证**（见出处 1）。这其实就是"局部规范化"的思路。

## 一个最容易搞混的例外：快照不是冗余

订单表里存"商品名"和"成交单价"，看起来违反 3NF——它们都能从商品表查出来。但仔细想：商品改名、调价之后，**历史订单应该显示下单那一刻的名字和价格**，不能跟着商品表变。

所以这两个字段存的是**当时的事实**，不是"商品当前信息的副本"。它们必须留在订单/订单明细里，不算违反范式，也不需要同步机制。

判断方法很简单：

- **能从别处实时查出来，且应该始终一致** → 叫冗余，要建同步和校对
- **必须留存当时模样，源数据变了也不能跟着变** → 叫快照，就该存

这个区分在 CRM、电商、账务系统里到处都是：合同上的客户名称、发票上的抬头、日志里的手机号，都是快照。

## 常见误区

- **"范式越高越好"**：错。BCNF、4NF、5NF 存在但实践里很少追，3NF 通常就是交易表的终点。
- **"冗余 = 乱设计"**：错。读多写少的场景里，冗余是正当的性能手段；乱设计是"没有主表、没有同步、没有校对"的冗余。
- **"为了性能先拍平再说"**：错。先看慢查询证据，再只冗余那几个高频字段，而不是整表拍平。
- **"快照违反范式要删掉"**：大错。删了历史单据就失真，这属于业务要求，不是设计瑕疵。
- **"1NF、2NF、3NF 都可以权衡"**：分寸不同。1NF、2NF 基本要守（带来的异常太难受），真正可以按场景权衡的主要是 3NF。

## 术语小抄

| 术语 | 含义 |
|---|---|
| 1NF / 原子性 | 一列不再包含多个可独立使用的值 |
| 主键 / 联合主键 | 唯一确定一行的一列或多列 |
| 完全依赖 | 非主键列依赖整个主键，而不是其中一部分 |
| 部分依赖 | 只依赖联合主键的一部分，违反 2NF |
| 传递依赖 | A → B → C，C 借 B 间接依赖 A，违反 3NF |
| 规范化 / 范式化 | 拆表消除冗余和不一致依赖 |
| 反范式 / 非规范化 | 故意加冗余字段减少联表，常见于读密集场景 |
| OLTP / OLAP | 联机交易处理 / 联机分析处理，前者重一致性，后者重查询性能 |
| 星型模型 / 雪花模型 | 数据仓库里"宽维表"与"规范化维表"的两种建模方式 |
| 快照 | 记录当时事实的字段，源数据变更后也不应跟着变 |
