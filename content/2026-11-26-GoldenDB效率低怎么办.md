上一篇讲了 GoldenDB 的 CN、DN、GTM 怎么分工。这次换个开发者视角：项目已经跑起来了，但接口慢、批跑慢、高峰期卡顿，官方一般怎么解决？

先给结论：**官方的套路是一个漏斗——先找慢 SQL，再看分片和索引，再让优化器少搬数据，最后用并行、分流和限流兜底。加机器通常是最后一步，不是第一步。**

以下内容按金篆信科官方文档与《中兴通讯技术》金篆数据库专题整理；具体能力以你实际使用的版本为准。

## 官方的排查顺序：先取证，再开药

1. **开发 / 迁移前**：用 CAC 做兼容性评估、分片键推荐；开发阶段用模拟数据压测，收集设计不合理的 SQL。
2. **上线前**：用 DBReplay 从 GoldenDB / MySQL / Oracle 录制负载并回放，评估语句兼容性和执行效率。
3. **生产监测**：用 Insight 看 QPS、TPS、慢 SQL、会话数、CPU、内存、磁盘、I/O 延迟；用内核 SQL 治理识别和拦截高危语句。
4. **定位根因**：用 `EXPLAIN` 看执行计划，判断是没索引、分片不对，还是数据被跨节点乱搬。
5. **对症优化**：改分片、加索引、SQL 改写、绑定执行计划、让算子下推。
6. **稳定性兜底**：读写分离、自动并行、流式查询、批量协议、SQL 限流、TP/AP 隔离。

> 大白话：别上来就说「数据库慢」。先问三件事：哪条 SQL 慢？它慢在哪一步？它是不是让一群机器做了无用功？答案清楚了，优化才有方向。

## 第 1 步：先把慢 SQL 揪出来

官方在某大型国有银行的实践里，把 SQL 治理做进了**数据库内核**，不是只在应用代码里查字符串。它能按三类规则识别慢 SQL：

- **按真实开销**：DML（增删改）和 DQL（查询）允许的最大执行时间、单次返回的最大结果集行数、多表关联的最大关联行数、单次执行和单会话允许读的最大数据块数；
- **按高危语法**：SQL 黑名单、禁止不带索引的查询（全表扫描）、禁止笛卡尔积、禁止随意 DROP / TRUNCATE；
- **按资源占用**：用户最大会话数、单会话和单条 SQL 的最大 CPU 时间、SQL 最大代价。

而且规则能按用户分开设：联机交易是高并发、低时延的短请求，最大执行时间可以卡在毫秒级；批量处理是大规模查询和更新，时间可以放宽到分钟级。

官方也提醒：生产上直接终止请求会影响业务成功率，更均衡的做法是**采集慢 SQL 列表，同步给应用团队在后续版本整改**。

## 第 2 步：看执行计划，别凭感觉

官方支持查看数据查询、插入、更新、删除的执行计划，而且可以只看 CN（计算节点）的计划、只看 DN（数据节点）的计划，或者两边一起看。目的就是看清执行顺序和执行瓶颈。

两个实用手段：

- `EXPLAIN`：看数据库准备怎么执行这条 SQL；
- `hint` / `outline`：给优化器提示，或把一条好计划在线绑定住。生产环境遇到紧急 SQL 性能问题，可以在数据库侧精准处理，**无需应用改写 SQL、无需启停**。

> 大白话：执行计划就是导航路线。`EXPLAIN` 把路线摊开给你看；`hint` 是跟导航说「走这条路」；`outline` 是把这条路收藏起来，以后默认都走它。

## 第 3 步：分片键选错，后面全白搭

分布式数据库里，数据按**分片键**（也叫分发键）散到不同 DN。官方给了几种分片策略：

- **哈希**：把数据均匀打散，适合大量等值查询；
- **范围**：按日期、数值分段，比如按自然月存；
- **列表**：按地区、机构代码这类枚举值存；
- **复制**：不常改的小表复制到每个节点，减少跨节点关联；
- **多级分片**：多法人这类精细场景，支持多层规则。

效率问题的常见根源是：**经常要关联的两张表，分片方式却不一样**，于是 JOIN 只能在计算层做，数据来回搬。官方给的办法是：

- 把有关联关系的表**采用相同分片策略**，让关联在本地完成；
- 用**数据重分布**在线调整分片键，把分发策略调一致；官方说多表可并发重分布，对在线业务影响秒级；
- 用**广播表**把小表复制到每个分片，JOIN 时本地就有；
- 用**全局索引**给非分片字段一个「第二查找键」：先查索引表拿到分发键，再定位目标分片，避免 SQL 群发到所有 DN。

> 大白话：分片键就是仓库地址。常一起查的表放同一个仓库；查不到地址时，先查索引表拿地址；常用的小手册每个仓库放一本。

官方还提供 CAC 工具，在迁移前就能做**分片键推荐**，别等上线后再拍脑袋改。

## 第 4 步：让计算靠近数据——下推

官方优化器分两层：

- **RBO（基于规则的优化）**：把长期实践验证过的规则固化下来，比如 `rownum` 转 `limit`、`not exists` 转 `left join`、`avg` 改写成 `sum` 和 `count`、过滤条件下推、视图展开；
- **CBO（基于代价的优化）**：按 `COST`（代价估算）选连接顺序。复杂场景里，小表驱动大表能显著减少从大表拉取的数据量。

物理优化阶段，官方明确列出了这些下推规则：JOIN 算子按分片规则下推、过滤算子下推到 DN、`in/not in` 子查询转成 `in` 函数下推、聚合算子先在 DN 分组聚合再由 CN 归并。如果聚合分组列正好带分片键，连二次归并都可以省掉。

> 大白话：别把一车货全拉到前台再挑。让每个仓库先过滤、先称好，只把结果报给前台，网络就不堵了。COST 就是优化器给每条路算的「过路费」。

## 第 5 步：索引和 SQL 改写，交给内核推荐

官方文章说得很直接：缺少合适索引时，一条 SQL 会生成低效执行计划，变成慢 SQL，持续挤占 CPU、内存和 I/O，严重时能让服务僵死。

传统外挂推荐工具的问题是：语法兼容性差、要下发大量统计 SQL、跟数据库自己的优化器「两张皮」。GoldenDB 的做法是把索引推荐做进内核：

- **内核集成**：直接复用数据库的解析器和优化器，复杂语法也能处理；
- **直方图采样**：小规模采样估算数据特征，不扫全表；官方给出的数字是**亿级大表 10 秒内完成分析**，对业务影响极小；
- **优化器协同**：模拟不同索引配置下的执行计划，按成本模型评估收益，保证推荐索引真能被采纳；
- **简单易用**：在 SQL 前加一个简单前缀语句，就能一键拿到推荐报告。

此外，官方还有 SQL 自动优化工具，能分析执行计划瓶颈，智能推荐**索引创建、语句改写、执行路径调整**三类建议。

> 一个提醒：白皮书提到 SKIP SCAN（索引跳跃扫描）要满足「前导列基数低、非前导列选择性高」，乱用反而有性能风险。工具给的是建议，不是免思考按钮。

## 第 6 步：分流、并行、批量、限流

当 SQL 和表结构都调过，官方还会用这些手段把高并发下的响应时间和稳定性兜住：

- **读写分离**：写操作发主节点，读操作按负载发备用节点；官方支持服务端口级、SQL 语句级、事务级、会话级粒度。实时性要求高的 SQL 走主节点，分析聚合类 SQL 走备节点，减少对主节点影响。
- **并行与自动并行度**：`Auto-DOP` 根据查询复杂度、数据分布和系统负载动态调整并行度；复杂查询拆成子任务分到不同节点并行执行，最后合并。
- **流式查询**：DN 到 CN、CN 到客户端都分批回响应，结果集不落盘；大结果集场景能降低等待时间和 CPU、内存占用。
- **批量协议**：官方证券方案里研发了 `batch Prepare` 新协议，适配大批量插入场景，性能提升 **60% 以上**；回放侧还用内存资源池、按事务分发减少系统调用。
- **SQL 限流**：不改重启就能限连接数、限最大结果集、拉黑不规范或超大请求的 SQL、绑定执行计划。
- **TP/AP 隔离**：复杂 AP 类 SQL 容易阻塞高优先级 TP 请求，造成「毛刺」。官方按 COST 识别计算密集型任务，交给独立异步线程组处理，让两类负载互不干扰。

## 术语小抄

| 缩写 / 术语 | 大白话 | 在本文里的作用 |
|---|---|---|
| SQL | 跟数据库说话的语言 | 你写的查询、增删改语句 |
| DML / DQL | 增删改 / 查询 | SQL 治理按这两类分别限时间 |
| CN / DN | 计算节点 / 数据节点 | CN 派活和汇总，DN 真存真算 |
| 分片键 / 分发键 | 数据放在哪个仓库的地址 | 决定关联查询要不要跨节点搬数据 |
| 广播表 | 每个仓库都放一本的小手册 | 小表 JOIN 时不用跨节点找 |
| 全局索引 | 第二查找键 | 用非分片字段查数据时先查地址 |
| 下推 | 把计算搬到数据旁边做 | 减少网络传输和 CN 负担 |
| 全表扫描 | 没按目录，逐页翻完整本书 | 常见慢 SQL 症状 |
| 笛卡尔积 | 两表没写关联条件，行数相乘 | 高危 SQL，官方直接禁 |
| RBO | 按经验规则优化 | rownum 转 limit、算子下推等 |
| CBO | 按代价估算优化 | 选连接顺序、小表驱动大表 |
| COST | 优化器算出来的过路费 | 判断 SQL 代价、识别重型任务 |
| EXPLAIN | 看执行路线图 | 找出 SQL 具体卡在哪一步 |
| hint / outline | 给导航提示 / 把路线钉住 | 不改应用也能调整或固定计划 |
| Auto-DOP | 自动决定派几个人并行干 | 复杂查询动态调并行度 |
| TP / OLTP | 一笔笔短平快的交易 | 高并发低时延，优先保障 |
| AP / OLAP | 复杂统计分析 | 耗时重，隔离到独立线程或节点 |
| HTAP | 一套系统同时做交易和分析 | 复杂查询走 AP 能力 |
| QPS / TPS | 每秒查询数 / 每秒事务数 | 监测负载和异常 |
| CAC | 迁移评估工具 | 迁移前推荐分片键、评估兼容性 |
| DBReplay | 负载回放工具 | 上线前用真实流量压测 |
| Insight | 运维管理平台 | 看慢 SQL、指标趋势、做限流 |

## 一句话记住

先在数据库里找出慢 SQL，再让数据少搬家、让计划走对路；实在扛不住，就分流、并行、批量、限流。加机器通常是最后一步，不是第一步。
