「我们系统拆成微服务了吗？」

拆了，拆了二十多个。结果改一条「满减规则」，要动商品、订单、促销、结算四个服务，拉四个组开会，上线还得一起排期。

这不是微服务，这是把单体切碎了，然后**把复杂度从代码里挪到了会议桌上**。Martin Fowler 对这种结果有个很准的说法：

> If the components do not compose cleanly, then all you are doing is shifting complexity from inside a component to the connections between components.
> 如果组件之间不能干净地组合，那你做的只是把复杂度从组件内部搬到了组件之间的连接上。

所以拆分的核心问题不是「切成几个」，而是**「沿什么缝切」**。缝找对了，各管一摊、各自发布；缝找错了，天天跨团队协调，比不拆还累。

这篇文章用一家**网上超市**贯穿到底，讲清楚四件事：切什么、切多大、边界画在哪、数据怎么分。最后给落地顺序和一张检查表。图在文末，六张，可放大看。

## 先记住一句话：按业务能力切，别按技术层切

大部分拆错，都错在第一刀。

管理者拿到一个大系统，最直觉的切法是按**技术层**：前端组、后端组、数据库组。Fowler 在 2014 年那篇经典文章里专门点了这个坑：

> When looking to split a large application into parts, often management focuses on the technology layer, leading to UI teams, server-side logic teams, and database teams.
> The microservice approach to division is different, splitting up into services organized around business capability.

微服务做法是按**业务能力**（business capability）切。一个服务覆盖这个业务领域的全栈：界面、存储、外部协作都归它，团队也得是跨职能的——有懂业务的、懂数据库的、懂用户体验的。

拿网上超市对照：

| 加一个「到货通知」需求 | 按技术层切（错） | 按业务能力切（对） |
|---|---|---|
| 要改什么 | 前端组改展示、后端组改接口、DBA 改表 | 库存组从页面到库表自己做完 |
| 要协调谁 | 三个组排期，谁先谁后 | 库存组一个组 |
| 出问题找谁 | 先定位是哪一层 | 直接找库存组 |

差别不在服务数量，而在**一次需求通常只惊动一个组**。microservices.io 把这个写成硬指标：

> The application also be decomposed in a way so that most new and changed requirements only affect a single service. That is because changes that affect multiple services requires coordination across multiple teams, which slows down development.

这也解释了为什么**康威定律**（Conway's Law）在微服务里被反复提起：

> Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure.
> 设计系统的组织，最终会造出和组织沟通结构同构的系统。

你按技术层分团队，就别指望长出按业务能力划分的服务。组织不变，图怎么画都白搭。图 1 把两种切法放在了一起。

## 第一刀：找「业务能力」，不是找「功能」

那业务能力到底是什么？microservices.io 的定义很朴素：

> A business capability is a concept from business architecture modeling. It is something that a business does in order to generate value.
> 业务能力是企业为了创造价值而做的事。

注意是「企业做的事」，不是「系统有的功能」。它常常对应一个业务对象：订单管理负责订单，客户管理负责客户。在线商店的例子里，业务能力是商品目录管理、库存管理、订单管理、配送管理。

怎么找？两个起点最实用：

1. **看组织结构**。公司里已经存在的那几个部门，往往就是天然的能力边界——它们已经在用不同的词汇说话了。
2. **看高层领域模型**。业务能力往往对应一个核心名词：商品、订单、客户、库存。

网上超市的价值链是：选品上架 → 逛店搜索 → 加购下单 → 支付 → 拣货配送 → 售后。每个环节背后都要有一个能力托住（图 2）。

这里还有个很值钱的细分，来自 DDD（领域驱动设计）的**子域**分类，microservices.io 的「按子域拆分」模式把它列得很清楚：

| 子域类型 | 含义 | 网上超市的例子 | 该投入多少 |
|---|---|---|---|
| Core 核心域 | 关键差异化，业务最值钱的部分 | 智能推荐、定价策略 | 自己精做，最好的人放这儿 |
| Supporting 支撑域 | 与业务相关，但不构成差异化 | 会员积分、优惠券 | 自研或外包都行 |
| Generic 通用域 | 不专属于这门生意 | 短信通知、文件存储 | 买现成的，别自己造 |

这一分类的实际用途是：**别把所有服务都当成同等重要**。给短信通知配一个三人小队长期维护，不如直接买云服务。

## 第二刀：切多大——不是越小越好

找到能力之后，最容易犯的错是觉得「既然拆，就拆细点」。

microservices.io 给的尺度是「两个披萨团队」：**6~10 人**，一个团队能独立开发、测试、部署它负责的服务，不需要天天求别人配合。同时借了两条面向对象设计的老原则：

- **单一职责（SRP）**：一个类只有一个改变的理由。放到服务上，就是一个服务只承担一组强相关的职责。
- **共同闭包（CCP）**：因为同一个原因改的东西，应该放在同一个包里。放到服务上，就是一次业务规则变化，最好只改一个服务。

Fowler 把这条说得更直白，也更好用：

> You want to keep things that change at the same time in the same module.
> 会同时变化的东西，应该放在同一个模块里。

> If you find yourself repeatedly changing two services together, that's a sign that they should be merged.
> 如果你发现自己总是一起改两个服务，那就是该把它们合并的信号。

这句话可以当成一条直接的**合并判据**：不用纠结理论边界，看过去半年的提交记录就行。两个服务总在同一批需求里一起动，说明它们本来就是一块。

反过来，拆太细的代价是实打实的。Fowler 提醒，把内存方法调用天真地换成 RPC，会变成啰嗦的通信（chatty communications），性能很差；一串同步调用还会带来**停机的乘法效应**——系统可用性变成各服务可用性的乘积。微软的 Azure 架构指南也把这条列进挑战清单：

> if the chain of service dependencies gets too long (service A calls B, which calls C...), the extra latency can become a problem.

三档对照可以这么看（图 3）：

| | 太粗 | 刚好 | 太细 |
|---|---|---|---|
| 一个服务 | 整个订单域 + 商品域 + 库存域 | 订单，或商品目录 | 订单查询、订单创建、订单关闭各一个 |
| 团队 | 一个大队，内部还是互相等 | 6~10 人端到端负责 | 一个小功能一个组，沟通比写代码多 |
| 一次需求 | 改一处，但发布要全系统回归 | 大多只动一个服务 | 动三四个服务，联调排期 |
| 典型症状 | 加个字段全量发版 | 各发各的 | A 调 B 调 C 调 D，链路一长就超时 |

一句话记住：**服务的大小，不是代码行数说了算，是「一个小组能不能从头到尾负责它、一次需求是不是大多只动它」说了算。**

## 第三刀：边界画在哪——同一个词，在不同地方不是一个意思

这是最容易被忽略、又最要命的一刀。

DDD 里有个核心模式叫**限界上下文**（Bounded Context）。Fowler 的解释是，DDD 通过把大系统切成一个个限界上下文来处理大模型，每个上下文内部模型是统一的，上下文之间再显式定义关系。

为什么要这么切？因为他直说了一句大实话：

> total unification of the domain model for a large system will not be feasible or cost-effective
> 对大系统做领域模型的完全统一，既不可行也不划算。

Fowler 举过一个电力公司的例子：同样是「meter」这个词，在公司不同部门嘴里，可能指电网与某个地点的连接、电网与某个客户的连接，也可能指墙上那块物理电表（坏了可以换）。日常聊天里这点歧义能糊过去，但到了精确的软件里就不行。他说「Customer」和「Product」是最常重复出现这种问题的两个词。

网上超市的「商品」也一样（图 4）：

| 在哪个上下文 | 「商品」指的是 | 关心的字段 |
|---|---|---|
| 商品中心 | 上架的档案 | 名称、图片、规格、上下架状态 |
| 订单 | 下单那一刻的快照 | 当时的价格、当时的名称，后来改价不影响历史订单 |
| 库存 | 仓库里可卖的东西 | SKU、批次、库位、可售数量 |
| 配送 | 包裹里的实物 | 重量、易碎标记、拣货位置 |

你会看到一个很有意思的现象：**这四个「商品」，谁都没错，但谁都不是全部**。硬要把它们合成一张「全字段商品表」，结果就是每个团队都往里加自己关心的字段，表越来越宽，谁都不敢改。

所以判断边界有个很土但好用的信号：

> **当一个词在不同部门嘴里意思不一样，那儿大概率就是一条缝。**

微软的指南给了一个更正式的说法：限界上下文是「业务内部天然划分，为领域模型提供一个显式的边界」。在这个边界里，模型和术语是自洽的；跨出去，就要做映射，而不是硬共用一张表。

## 第四刀：数据必须跟服务走

前三刀切的是职责，这一刀切的是**数据库**。它是判断「真微服务」和「假微服务」最容易验证的一条。

microservices.io 的 **database per service** 模式要求：

> Keep each microservice's persistent data private to that service and accessible only via its API. A service's transactions only involve its database.
> 每个微服务的持久化数据对它私有，只能通过它自己的 API 访问；服务的事务只涉及它自己的数据库。

注意它并不要求「一个服务一台数据库服务器」。同一台 MySQL 上，给每个服务一组私有表、或一个独立 schema，都是合格做法——schema 方式边界更清晰，开销也低。真正要防的是别的服务绕过 API 直连你的表。越多团队共用一个库，改一个字段就越像拆炸弹。

但这一刀是要付代价的，而且必须提前认（图 5）：

| 以前一个库里很轻松的事 | 拆完之后 |
|---|---|
| 下单同时扣库存，一个事务搞定 | 跨服务事务很难。分布式事务因 CAP 受限，很多 NoSQL 干脆不支持。通常改用 **Saga**：一步一步做，失败走补偿，接受**最终一致** |
| `SELECT ... JOIN` 把客户和订单拼起来 | 数据库层做不了了。要么 **API 组合**：应用层先取客户、再取订单，自己拼；要么 **CQRS**：维护一张订阅事件更新的查询视图 |
| 改一次表结构，通知一个 DBA | 多套 SQL/NoSQL 要分别管 |

Fowler 对这件事的提醒很克制也很诚实：分布式事务出了名地难实现，所以微服务架构强调无事务协调，明确承认一致性可能只是最终一致，问题靠补偿操作解决；「只要修复错误的成本低于更强一致性下损失的业务，这个取舍就值」。

所以拆服务之前，先回答一个问题：**「下单扣库存」这种跨服务的事，你打算怎么处理？** 如果答不上来，拆完的第一个月就会在半夜修数据。

## 怎么落地：别停机重写，用绞杀者模式

刀法定了，下一个问题是：现有系统还在跑，怎么换？

最诱人的方案是「停服，照原样重写一遍，一次切过去」。Fowler 说这种听起来简单的计划，大多数时候都烧得一塌糊涂：替换一个正经 IT 系统要很久，用户等不了新功能；旧系统的细节很难搞清；更糟的是，很多行为本来就不该要，照抄等于白做。

他推荐的是**绞杀者模式**（Strangler Fig）。名字来自一种榕树：种子落在宿主树的树杈上发芽，长到地面扎根、长到树冠见光，然后自给自足，最后宿主树死去，留下榕树形如旧树的轮廓。

> Like the fig, it begins with small additions, often new features, that are built on top of, yet separate to the legacy code base. As we do this we move bits of behavior from the legacy system into the new code base.

落到网上超市，顺序大致是（图 6）：

1. **先加统一入口**。API 网关挡在前面，后面是旧单体，用户无感。
2. **新功能直接建在新服务里**，构建在旧系统之上但代码分离。比如「到货通知」，别往老单体里加。
3. **挑一块边缘业务搬出来**。优先选变更频繁、读多写少、边界本来清楚的那块——库存查询比核心账务适合当第一刀。
4. **搬一块，切一块流量**，验证没问题再扩大。新旧共存期间需要一层「过渡架构」，用完就删。Fowler 专门说，别嫌这层代码浪费：降低的风险和更早拿到的收益，比它的成本高。
5. **旧单体最后只剩空壳**，再下线。

Fowler 引用 Ian Cartwright 等人把这类渐进式现代化归纳成四件事：想清楚要的结果、决定怎么拆成小块、把小块交付出去、调整组织让这件事能持续发生。他特别强调，顺序不表示先后，四件事要一起推进——如果组织和文化不变，新系统最后也会长成老系统那副样子。

## 什么时候别拆

微服务不是进步的象征，是一种**用分布式复杂度换组织自治**的交易。账算不过来，就别换。

Fowler 的原话甚至更直接：

> One reasonable argument we've heard is that you shouldn't start with a microservices architecture. Instead begin with a monolith, keep it modular, and split it into microservices once the monolith becomes a problem.

他也补了一句：这个建议并不完美，因为好的进程内接口通常不是好的服务接口。但方向是明确的——**先把单体模块化，等它真的成了问题再拆**。

下面几种情况，建议先别动刀：

- 团队就三五个人，一个人能把所有模块装进脑子；
- 业务边界还没稳定，这个月的核心域下个月就变了；
- 没有 CI/CD、集中日志、链路追踪，发布全靠人肉；
- 主要需求是强事务的（例如核心账务），暂时接受不了最终一致；
- 说不清拆完到底省了什么，只是「大家都在拆」。

微软的指南列了八类挑战可以作为对照：复杂性、开发与测试、治理缺失、网络拥塞与延迟、数据完整性、管理（成熟 DevOps）、版本兼容、团队技能。最后一条尤其实在：微服务是高度分布式的系统，得先评估团队有没有那个经验和能力。

## 七个常见坑，对照着自查

| 坑 | 表现 | 正解 |
|---|---|---|
| 按技术层切 | 前端/后端/DBA 三个组，一个需求三方排期 | 按业务能力切，团队跨职能 |
| 觉得越小越好 | 服务几十个，一次需求动四五个，链路越拉越长 | 6~10 人一队，一起改的合并 |
| 共用数据库 | 服务名义上分开，实际都连同一张表 | 数据私有，只能通过 API；schema 隔离也算合格 |
| 本地调用直接换 RPC | 把一个方法拆成三次远程调用，接口又细又碎 | 接口粗粒度，尽量异步消息；smart endpoints, dumb pipes |
| 组织没跟着变 | 服务拆开了，开会还是原来那几个部门一起 | 按康威定律调整组织，让团队完整负责一个能力 |
| 没有自动化就拆 | 发布靠人工协调，一次上线两小时 | 先把 CI/CD、监控、日志补齐 |
| 照抄大厂服务数量 | 「人家拆了上百个，我们也要」 | 人家有平台团队和基础设施，先算自己的账 |

顺带解释一下表里的 **smart endpoints, dumb pipes**（智能端点、哑管道）：业务逻辑放在服务自己身上，通信管道只负责可靠地传消息，别把路由规则、业务编排塞进中心化的总线里。常见实现就是 HTTP API 加轻量消息中间件。把复杂逻辑塞进管道，等于造了一个新单体，还更难改。

## 动手前的八问

把这张表存下来，拆之前逐条答：

1. 这块业务能用一句话说清「它负责什么、不负责什么」吗？
2. 一个 6~10 人的小组能端到端负责它吗？
3. 最近半年的需求里，有多少次只动这一块？
4. 它会不会总跟另一个服务一起改？（会 → 先合并，别拆）
5. 它的数据能不能独占？谁有权限改？
6. 跨服务的事务和查询，方案想好了吗？
7. CI/CD、集中日志、指标、链路追踪，齐了吗？
8. 拆完比现在**具体**省了什么？（说不出来就先别拆）

## 术语小抄

| 术语 | 大白话 |
|---|---|
| 业务能力 | 企业为创造价值而做的事，例如「订单管理」，不是「一个接口」 |
| 子域（core/supporting/generic） | 核心域=看家本领，支撑域=配套，通用域=买现成的 |
| 限界上下文 | 一个词有确定含义的范围；出了这个范围，同名不同义 |
| DDD | 领域驱动设计，用业务语言建模型，而不是一上来画表结构 |
| 康威定律 | 系统结构会长成组织沟通结构的样子 |
| SRP | 单一职责：一个服务只有一个改变的理由 |
| CCP | 共同闭包：因为同一原因改的东西放一起 |
| 两个披萨团队 | 6~10 人，能独立开发和部署自己服务的组 |
| Database per service | 每个服务的数据私有，别人只能通过 API 访问 |
| Saga | 跨服务事务的替代方案：分步执行，失败走补偿 |
| 最终一致 | 不保证立刻一致，但保证一段时间后一致 |
| API 组合 / CQRS | 跨服务查询的两种做法：应用层拼结果 / 维护查询视图 |
| 绞杀者模式 | 新功能长在外面，逐步替换旧系统，最后旧系统退场 |
| 分布式单体 | 服务拆开了，但仍然要一起发布、一起改，最坏的两头都占 |

2. Martin Fowler, [BoundedContext](https://martinfowler.com/bliki/BoundedContext.html)（2014）：限界上下文定义、电表与 Customer/Product 一词多义的例子。
3. Martin Fowler, [StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html)（2024 修订）：绞杀者模式的比喻、四件事、过渡架构与组织变革。
4. microservices.io, [Decompose by business capability](https://microservices.io/patterns/decomposition/decompose-by-business-capability.html)：业务能力定义、SRP/CCP、两个披萨团队、识别起点。
5. microservices.io, [Decompose by subdomain](https://microservices.io/patterns/decomposition/decompose-by-subdomain.html)：core / supporting / generic 三类子域。
6. microservices.io, [Database per service](https://microservices.io/patterns/data/database-per-service.html)：数据私有、三种隔离方式、跨服务事务与查询的代价。
7. Microsoft Learn, [Microservices architecture style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices)：收益与挑战、最佳实践、避免过度细分。
8. Eric Evans, *Domain-Driven Design: Tackling Complexity in the Heart of Software*：限界上下文的原始出处（第四部分 Strategic Design）。

文中的网上超市、团队规模和上线顺序为便于理解的教学示例，不是任何具体公司的实践记录；Fowler 与 microservices.io 的引文为原文或直译，工程建议部分标明为经验做法。
