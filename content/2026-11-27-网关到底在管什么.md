"网关"这个词最坑的地方在于：所有人都觉得自己懂。

说"就是个转发"的，和说"就是 Nginx"的，和说"就是微服务那个 API Gateway"的，聊十分钟会发现各自脑子里是三样东西。有人以为它做鉴权，有人以为它做负载均衡，还有人把它当成限流器。

所以这篇不先讲产品，先把**概念**按权威文档钉死，再说它在生产里到底干什么活、不干什么活。

> 一句话版本：网关是**唯一入口**，它对外冒充一台服务器，对内替所有服务做那些"每个服务都要重复做一遍"的事。

## 先按官方定义把概念钉死

### RFC 9110：网关就是"反向代理"，而且它冒充源站

HTTP 协议的标准文档 RFC 9110 在第 3.7 节定义得很干脆：

> A "gateway" (a.k.a. "reverse proxy") is an intermediary that acts as an origin server for the outbound connection but translates received requests and forwards them inbound to another server or servers.

翻译过来就三层意思：

- **它对外是"源站"**。客户端握手、看证书、收响应码，全程以为自己在跟那台服务器对话。
- **它翻译并转发**。"translates received requests" 这个词很关键——不是照抄，是可以改的（改路径、改头、换协议）。
- **它向内转发**。真正干活的是后面那些服务器，客户端一辈子看不到它们的地址。

RFC 还顺手写了它最典型的三个用途：

> Gateways are often used to encapsulate legacy or untrusted information services, to improve server performance through "accelerator" caching, and to enable partitioning or load balancing of HTTP services across multiple machines.

即：**把老系统或不可信的服务包起来、做加速缓存、把 HTTP 服务分区并负载均衡到多台机器**。注意这三条没有一条是"写业务逻辑"。

**大白话：**小区门禁的保安，长得像"物业的人"，访客把他当成了要办事的那一方（冒充源站）；他核对证件、登记、指路，但**他不开锁、不搬货、不签合同**（不干业务）。货真价实在楼里干活的，是那些你见不到的部门。

这里还有个容易被忽略的方向问题。同一份 RFC 里，"proxy"（正向代理）是**客户端自己选的**，帮你出门；"gateway / reverse proxy"是**服务端自己装的**，替服务器挡门。方向反了，责任也就反了：正向代理出问题是你自己的事，网关出问题是全站的事。

### microservices.io：它为什么在微服务里变成必需品

Chris Richardson 在 microservices.io 的 API Gateway 模式里写得更直接：

> Implement an API gateway that is the single entry point for all clients. The API gateway handles requests in one of two ways. Some requests are simply proxied/routed to the appropriate service. It handles other requests by fanning out to multiple services.

两种处理方式，这句话把网关的能力边界划清了：

1. **proxy / route**：一对一转发。`/api/order/*` 转给订单服务，就这么简单。
2. **fan out**：一个请求扇出到多个服务，再把结果拼起来。这就是为什么网关常和 API 组合（API Composition）一起出现。

它还列了网关真正的价值（原文措辞我保留，后面加白话）：

- **Insulates the clients from how the application is partitioned**：服务怎么切、切几个，客户端不用知道。
- **Insulates the clients from the problem of determining the locations of service instances**：实例 IP 怎么变、扩了几台，客户端不用改配置。
- **Provides the optimal API for each client**：给 Web、App、第三方各一套合适的接口，这就是 BFF（Backends for frontends）变体的由来。
- **Reduces the number of requests/roundtrips**：手机端一次请求拿齐，而不是调五个接口。
- **Simplifies the client by moving logic for calling multiple services from the client to API gateway**：把"调五个服务再拼装"的逻辑从端上搬到网关。
- **Translates from a "standard" public web-friendly API protocol to whatever protocols are used internally**：对外 HTTP，对内 gRPC、Dubbo、老系统的私有协议，网关来做翻译。

同时它也没藏着代价，这两条我特别认：

> Increased complexity - the API gateway is yet another moving part that must be developed, deployed and managed.
>
> Increased response time due to the additional network hop through the API gateway - however, for most applications the cost of an extra roundtrip is insignificant.

**大白话：**网关不是免费的。它是"又多了一个要开发、要部署、要盯着、要背锅的部件"，而且实打实多一跳网络。所以别把它当性能优化手段——它优化的是**治理成本**，不是延迟。

### AWS 的表述：它是"前门"，管四件事

AWS 对自家 API Gateway 的定位，可以当成"生产职责清单"来看：

> API Gateway acts as a "front door" for applications to access data, business logic, or functionality from your backend services.

> API Gateway handles all the tasks involved in accepting and processing up to hundreds of thousands of concurrent API calls. These tasks include traffic management, authorization and access control, monitoring, and API version management.

注意后半句的四个词：**traffic management、authorization and access control、monitoring、API version management**。这就是生产里网关的四大类工作。至于"几十万并发"是 AWS 托管服务的规模，不是自建网关的承诺，别照抄。

## 一个请求进门，要过八道工序

前面都是定义。落到线上，一个请求从公网进来，网关大致要做这些事——顺序不是随便排的：

1. **TLS 终止**：证书在这里卸下。续期、换证书只改一处，不用每个服务都装一遍。
2. **路由匹配**：按 Host、Path、Header 决定这条请求归谁。`/api/order/*` → order-svc。
3. **认证与授权**：验签、查过期、看 scope。过了就把身份写进 Header（`X-User-Id`、`X-Tenant`）传给下游。
4. **限流与配额**：按 IP、用户、应用维度计数，超了直接 429，别打到后端去。
5. **请求改写**：去前缀、补 Header、加 `X-Request-Id`，让后端看到干净的接口。
6. **负载均衡**：按权重或最少连接挑一个健康实例。灰度时"5% 走新版本"就发生在这里。
7. **重试与熔断**：连不上换一台；连续失败就熔断，别把整条链路拖死。
8. **日志、指标、链路追踪**：耗时、状态码、上游地址、trace id。排障第一个看的就是这里。

为什么要这个顺序？**越便宜、越能早拒绝的检查越靠前。** 让 100 万次恶意请求先去解 JWT，CPU 会先被打满，后端的限流规则根本没机会生效。

**判断一个功能该不该放网关，问两句就够：**

- 是不是**所有入口都要**？是 → 放网关；只有一个服务要 → 放服务里。
- 是不是**不需要业务数据就能判断**？需要查库、算价格、看库存 → 别放网关。

两条都满足才放。只满足一条还硬放，网关就会慢慢长成第二个业务系统——这是"分布式单体"最常见的诞生方式。

## 它站在哪：南北向是门，东西向是楼道

这是最容易混的一段。

- **南北向（North-South）**：外部用户进来的流量，纵向穿过多层网络边界。网关就站在这里。
- **东西向（East-West）**：服务之间互相调的流量，横向发生在集群内部。

为什么必须分开？因为**两段流量的信任级别不一样**。门外的请求不可信，要查证件、要限速、要防攻击；楼道里的请求是自家服务发的，重点是跑得快、断了能绕。

Istio 的官方文档把这个位置说得很清楚：

> Gateway configurations are applied to standalone Envoy proxies that are running at the edge of the mesh, rather than sidecar Envoy proxies running alongside your service workloads.

**网关跑在网格边缘，是独立进程，不是服务旁边那个 sidecar。** 这句话顺手解决了一个常见扯皮：出问题时到底是"网关的锅"还是"网格的锅"——先看它是不是同一个进程。

生产里常见的错位是：拿对外的 API 网关去跑服务间调用。后果很具体——所有内部请求都绕一次边缘、扛一次公网级限流规则，还多一个全局单点。内部那一层该交给服务网格（mTLS、重试、熔断、流量拆分），跟着服务走，而不是集中在一处。

## 它能做多少，取决于站在四层还是七层

- **四层（L4，传输层）**：只看得到 IP 和端口。像邮局只看信封地址，能投递，但不拆信。所以它能转发 MySQL、Redis、MQ 的 TCP 连接，却不知道里面是不是 HTTP。
- **七层（L7，应用层）**：能读到方法、路径、Header、Cookie。像前台拆开看内容，才知道该转给哪个部门、要不要登记。

这个差别决定了能力：

| 想做的事 | 四层够不够 | 说明 |
| --- | --- | --- |
| 按 IP / 端口转发 | 够 | LVS、F5、HAProxy（TCP 模式） |
| 按 URL 路径路由 | 不够 | 必须看到 HTTP 请求行 |
| 验 token、按用户限流 | 不够 | 必须读到 Authorization 头 |
| 按 Header 灰度 | 不够 | 必须解析请求头 |
| 协议转换（HTTP/1.1 ↔ HTTP/2、REST ↔ gRPC） | 不够 | 必须理解应用层语义 |
| 数据库代理、纯长连接 | 够，而且更快 | 不需要理解内容 |

Envoy 官方对自己的描述就是这两种身份的合体：

> Envoy is an L7 proxy and communication bus designed for large modern service oriented architectures.

同时它底层是 "L3/L4 filter architecture"，上面再叠一层 "HTTP L7 filter" 做缓冲、限流、路由。这也是为什么同一个产品既能当边缘网关，也能当 sidecar。

**代价要说清楚：**上了七层，每个请求都要解析，瓶颈从"带宽"变成"CPU 和连接数"。容量评估的口径要跟着变——不是"能扛多少连接"，而是"每秒能解析多少请求"。

## 都叫"网关"，其实是五个工种

架构图上经常同时出现五个东西，名字里都带"网关"或"代理"，但职责完全不同：

| 角色 | 站在哪 | 主要职责 | 典型产品 | 别让它干 |
| --- | --- | --- | --- | --- |
| 负载均衡 | 最外层 | 把连接分给多台机器，剔除不健康实例 | LVS、F5、云 SLB/NLB | 判断"这个用户是谁" |
| 流量网关 | 边缘、公网入口 | TLS 终止、WAF、静态缓存、域名与路径分流 | NGINX、Envoy、OpenResty | 细粒度业务鉴权、API 计费 |
| API 网关 | 边缘之后 | 鉴权、配额限流、API 版本与生命周期、开发者门户 | Kong、APISIX、AWS API Gateway | 跨服务的复杂聚合 |
| BFF / 业务网关 | 贴近某一端 | 为 Web / App / 小程序聚合裁剪接口 | 自研、GraphQL | 承担全站通用治理 |
| 服务网格 sidecar | 每个服务旁边 | 服务间 mTLS、重试、熔断、流量拆分、追踪 | Istio、Linkerd、Envoy | 管外部用户的认证 |

**负载均衡和网关的区别，一句话：**负载均衡解决"分给哪台机器"，网关解决"这个请求该不该、能不能、按什么规则到达应用"。是先后关系，不是替代关系。

Kubernetes 的答案很值得抄。官方把网关拆成三个角色：

- **GatewayClass**：定义"谁来实现"这类网关（哪个控制器管）。
- **Gateway**：定义一个**流量处理基础设施的实例**，比如一个云负载均衡器。原文是 "Defines an instance of traffic handling infrastructure, such as cloud load balancer."
- **HTTPRoute**：定义"从 Gateway 的 listener 到后端"的具体路由规则。

对应到组织上，就是**基础设施团队管 GatewayClass 和 Gateway，应用团队只写 HTTPRoute**。职责分清，才不会出现"改个路由要等两周排期"或者"网关配置没人敢动"。

小团队最常见的正确解：**一个流量网关（Nginx 或 Envoy）+ 一个 API 网关**。BFF 和网格等真有痛点再上。每多一跳，就多一个要配超时、要看指标、要背责任的地方。

## 六个坑，几乎每个团队都踩过

网关上线不难。难的是它成为唯一入口之后，所有的超时、重试、IP、容量问题都会在这里集中爆发。

**坑 1：超时层层相等。** 客户端 3s、网关 3s、服务 3s。结果网关刚超时断开，服务还在算，算完白算；上游一重试，请求量翻倍。正确做法是超时当**预算**来分配，外层必须比内层大：

| 层级 | 超时预算 | 理由 |
| --- | --- | --- |
| 客户端 | 5s | 用户体验上限 |
| 网关 | 2s | 留 3s 给网络与重试 |
| 业务服务 | 1s | 留 1s 给下游 |
| 数据库 / 缓存 | 800ms | 留 200ms 给连接与序列化 |

**坑 2：给所有请求配自动重试。** 下单接口超时被重试三次，用户被扣三次钱。只对幂等请求（GET / PUT / DELETE）重试；POST 要重试，后端必须先有幂等键去重。

**坑 3：网关把请求体整个读进内存再转发。** 几个大文件上传就能把网关内存打满，全站 502，而业务服务却很闲。要设 body 上限，大文件走流式或对象存储直传。

**坑 4：日志里记的客户端 IP 全是网关自己的。** 风控拿不到真实 IP，按 IP 限流失效，攻击时定位不到来源。要传 `X-Forwarded-For` / `X-Real-IP`，而且**只信任自己网段的代理头**——这个头可以被伪造，直接取第一个值等于把风控交给攻击者。

**坑 5：上线时改了路径前缀，网关没同步。** 本地 200，线上 404：`/api/order` 被转成 `/order`，服务端一个都不认识。前缀改写规则要和后端的 context-path 成对变更，进配置评审，配回归用例。

**坑 6：容量按业务峰值算，忘了网关自己也是瓶颈。** 业务服务扩到 50 台，网关还是 2 个实例，先挂的永远是它。L7 的瓶颈是 CPU 和连接数，独立压测、独立扩容，至少三个实例跨可用区。

**排查顺序**也顺手记一下：先看网关自己的指标（QPS、4xx/5xx、上游连接数、CPU），再看上游服务的耗时。

- 网关 5xx 且上游**没有**日志 → 多半连不上或超时。
- 网关 4xx 且上游**没有**日志 → 多半是鉴权或限流拦下的。

责任划分清楚了，半夜就不用拉三个团队开会。

## 什么时候该上，什么时候别上

这一段是我的判断，不是官方说法：

**该上：**

- 有多个客户端（Web、App、小程序、第三方），需要统一入口和不同的接口形态。
- 有统一的横切需求：认证、限流、灰度、审计、计费。写在每个服务里必然走样。
- 后端实例地址经常变（容器化、弹性伸缩），不能让客户端跟着改。

**别上，或者先别上：**

- 就一个单体应用、几个服务，前面放个 Nginx 做反向代理和 TLS 就够了。RFC 里"网关"本来也包含这个层次，不必因为名词高级就上 API 网关。
- 团队没人能维护它。网关是**唯一入口**，它的可用性要求高于任何单个业务服务；没有主人、没有压测、没有告警的网关，比没有网关更危险。
- 有人打算在里面写业务逻辑。一旦开始"在网关上做个判断"，它就从基础设施变成了没人敢改的核心系统。

最后一个观点：**网关应该被当成产品来治理，而不是当成一台服务器来运维。** 路由、插件、证书、配额都要有版本、有评审、有回滚。Kubernetes Gateway API 花那么大力气做角色分离，本质就是把"谁能改什么"变成结构问题，而不是靠流程和人情。

## 术语小抄

| 术语 | 大白话 |
| --- | --- |
| 网关 Gateway | 唯一入口，对外冒充源站，对内转发并做公共治理 |
| 反向代理 Reverse Proxy | 装在服务端、替服务器挡门的代理；RFC 里与网关同义 |
| 正向代理 Forward Proxy | 装在客户端侧、帮你出门的代理，和网关方向相反 |
| 南北向 North-South | 外部用户进系统的流量，纵向穿边界 |
| 东西向 East-West | 服务之间互调的流量，横向在集群内 |
| Ingress | Kubernetes 里"外部流量怎么进来"的一类资源，Gateway API 是它的后继 |
| L4 / L7 | 传输层 / 应用层。前者看 IP 端口，后者能读 HTTP 内容 |
| TLS 终止 | 在网关卸下 HTTPS，后面走明文或内部再加密 |
| SNI | TLS 握手里带的域名，网关靠它决定用哪张证书 |
| 上游 / 下游 Upstream / Downstream | 消息流的方向：上游往上下游走；inbound 指朝源站，outbound 指朝用户 |
| 限流 Rate Limiting | 单位时间放多少请求，常见算法是令牌桶、漏桶、滑动窗口 |
| 熔断 Circuit Breaker | 连续失败就"跳闸"，一段时间内直接拒绝，避免拖死整条链路 |
| 重试 Retry | 失败再试一次；只对幂等请求安全 |
| 幂等 Idempotent | 同一个请求做一次和做十次结果一样（GET、PUT、DELETE 通常幂等） |
| BFF | Backend for Frontend，为某一端专门做的聚合层 |
| sidecar | 和服务部署在一起、跟着服务走的代理进程 |
| 服务网格 Service Mesh | 用一堆 sidecar 管服务间通信的基础设施 |
| WAF | Web 应用防火墙，挡 SQL 注入、XSS 这类攻击 |
| X-Forwarded-For | 记录请求经过的代理链，用来还原真实客户端 IP |
| 金丝雀 / 灰度 Canary | 先放一小部分流量到新版本，看指标再全量 |
| API 生命周期 | API 从设计、发布、版本演进到下线的管理过程 |
| 429 / 502 / 504 | 被限流 / 上游返回异常 / 网关等上游超时，网关排障三板斧 |
