Redis 用久了你会发现，最难受的不是命令记不住，而是**三个月前随手起的一个 key，现在没人敢动**。

- `user_data_1001` 到底是用户资料还是用户订单？
- `a:1:b:2` 的分层到底按什么规则？
- 一个 key 里塞了 10MB 的 JSON，删也不是、不删也不是。
- 上了集群之后，两个 key 死活不能放在一条事务里，报 `CROSSSLOT`。

这些问题都不是 Redis 的锅，是 **key 设计**没做在前面。

Redis 的 key 有点像数据库的表结构：一旦线上有数据，改名就意味着迁移。所以在一开始就按规则设计，比事后补救便宜得多。

先把六条原则记住：

| 原则 | 一句话 | 不做的后果 |
|---|---|---|
| 分层 | `业务:实体:ID:字段`，冒号分隔 | 看不懂、扫不出、没法按前缀分组 |
| 定长 | 约 20～50 字节，别塞 URL 和 JSON | 每个字典项都被长 key 放大，吃内存 |
| 干净 | 可打印 ASCII，不用空格 / 换行 / 通配符 | 命令行、监控、日志切分处处踩坑 |
| 带版本 | 格式会变就加 `v1` / `v2` | 新旧格式混在一起，无法灰度 |
| 拆大 | 字段多用一个 hash，成员多分桶 | 删除、迁移、AOF 重写卡顿 |
| 看集群 | 多 key 原子操作加 `{tag}` | `CROSSSLOT`，事务和 Lua 用不了 |

下面六张图从"解剖一个 key"讲到"上线后怎么排查"，每张图下面都有「怎么看」，照着读就行。

## 先立住基准：key 对 Redis 来说到底是什么

很多争论源于一个误解：**冒号不是语法**。

Redis 眼里的 key 就是一个**二进制安全的字节串**——你可以放中文、放空格，甚至放不可见字符。`SET bike:1 Deimos` 里的冒号只是给人看的，Redis 不会因为冒号就搞出"层级"这种概念。

那为什么还要用冒号？因为**人需要层级，工具需要前缀**：

```bash
# 业务读写：整串就是一个 key
GET shop:product:1001:stock

# 排障时按前缀扫一组 key（生产用 SCAN，不用 KEYS）
SCAN 0 MATCH shop:product:1001:* COUNT 100

# 按业务域做数据迁移、设淘汰策略，也靠前缀
SCAN 0 MATCH shop:product:* COUNT 500
```

所以 key 设计其实是同时在满足两个对象：

- **人**：一眼看懂这是谁的什么数据；
- **机器**：能算槽位、能按前缀批量操作、别让一个槽位扛下所有流量。

> **术语小抄 · 二进制安全（binary safe）**
> 指 Redis 不假设 key/value 是文本，允许里面出现任意字节（包括 `\0`）。所以中文 key 在技术上完全合法，只是字符集、日志转义、命令行复制粘贴这些环节容易出岔子，团队里一般统一用 ASCII。

## 一、分层：给 key 一个能念出来的结构

最好用的通用模板是四段：

```
业务域 : 实体类型 : 标识ID : 字段/用途
```

对应到图上就是 `shop:product:1001:stock`——电商域、商品实体、编号 1001、库存字段。

Redis 官方文档的入门示例用的是更短的两段式 `bike:1`（对象类型 + 编号）。生产上字段一多，再加两段就很自然。

**分层的价值在排障时最能体现。** 某天告警说"库存接口慢了"，你直接 `SCAN ... MATCH shop:product:*:stock` 就能把所有库存键捞出来看 TTL 和大小。如果当初写的是 `product_info_1001_stock`，这个 pattern 就写不出来。

几个常见场景可以这样套：

| 场景 | 推荐 key | 说明 |
|---|---|---|
| 对象缓存 | `shop:product:1001:detail` | 四段齐全，最标准 |
| 分布式锁 | `lock:order:88` | 锁前缀单独一类，方便统一清理 |
| 按天限流 | `rate:uid:1001:20261127` | 粒度写进 key，过期也好设 |
| 计数 | `cnt:article:42:like` | 计数前缀，便于监控 |
| 会话 | `sess:web:uid:1001` | 多端会话用第二段区分 |
| 幂等去重 | `idem:pay:req:9f3a...` | 请求号做 ID，TTL 覆盖去重窗口 |

**什么时候加版本号？** 只要 value 的序列化格式可能变，就在 key 里带一段 `v1` / `v2`，例如 `shop:product:1001:detail:v2`。这样新旧格式能共存，灰度上线不用一次性清缓存。

## 二、长度：甜点区在 20～50 字节

key 太短省了几个字节，但**语义丢了**：`u:1` 里的 `u` 是 user 还是 unit？`v2` 是版本号还是业务名？三个月后连写它的人都不敢确定。

key 太长则相反，问题会被**乘以数据量**：

- 每个 key 都有字典项、指针、过期时间等固定元信息，长 key 让每份开销都变大；
- 一亿个小对象，key 多出来的 10 个字节就是 10 亿字节；
- 慢日志、AOF、RDB 里也全都要带着这串长 key。

典型的超长写法是把 URL 或 JSON 当 key：

```
# ✕ 别这么写
cache:https://shop.example.com/api/v2/products/1001?utm_source=app&...

# ✓ 只留必要标识
shop:product:1001:detail
```

经验区间是 **20～50 字节**，四段以内，用可打印 ASCII。这不是 Redis 的硬限制（key 上限是 512MB），是工程上的甜点区。

### 官方给的两条省内存思路

Redis 内存优化文档里有两个很实在的结论，值得单独拎出来：

**① 能用 hash 就别用一堆 key。** 官方文档原话是小聚合类型"最高省 10 倍内存，平均省 5 倍"。如果你有一个用户对象要存 name、email、age，用四个 key 不如用一个 hash 的四个 field。

**② 能用位图就别一个用户一个键。** 官方文档举例：用户 ID 是自增整数时，用 `SETBIT` 记录订阅状态，**1 亿用户只要约 12MB**。把"ID 放进 key"改成"ID 放进位偏移"，是数量级的差别。

> **术语小抄 · 紧凑编码（listpack / ziplist）**
> Redis 对小 hash、小列表、小有序集合会用一块连续内存来存，而不是建真正的哈希表。这样省内存、CPU 缓存命中也好。默认阈值是 hash 512 项 / 单值 64 字节，超过了会自动转成普通编码——转了之后省内存的效果就没了。可以用 `OBJECT ENCODING key` 看当前用的哪种。

## 三、大 key：一个 10MB 的键能拖慢整个实例

这里说的"大 key"是**value 大**，不是名字长。典型症状：

- 一个 Set 里塞了几百万个成员；
- 一个 String 里塞了 10MB 的 JSON；
- 一个 Hash 里塞了全量用户资料。

它的麻烦不在读写那一下，而在**需要整块搬运的时候**：删除会阻塞、主从迁移会卡、AOF 重写会慢，甚至集群做 slot 迁移都会出问题。

### 官方给的数字：11 MB → 1.7 MB

Redis 内存优化文档里有一个非常经典的例子。假设要缓存 10 万个这样的对象：

```
object:102393
object:1234
object:5
```

**写法 A：一个对象一个 key**

```bash
SET object:102393 somevalue
SET object:1234 somevalue
SET object:5 somevalue
```

官方实测：约 **11 MB**。

**写法 B：拆成 hash + 预分片**

把 key 的后两位拿出来当 hash 的 field，前面部分当 key：

```bash
# object:1234 → key 是 object:12，field 是 34
HSET object:12 34 somevalue

# object:102393 → key 是 object:102，field 是 393
HSET object:102 393 somevalue

# 数字太短时，key 用 "object:"，整个数字当 field
HSET object: 5 somevalue
```

官方实测：约 **1.7 MB**。差了 6 倍多。

这个技巧的本质是：把 10 万个顶层字典项，压缩成约 100 个 hash，每个 hash 里约 1000 个 field（文档里说约 100 个是 CPU / 内存的最佳折中）。因为 ID 都以数字结尾，天然就实现了"预分片"。

### 拆的时候要知道的两个代价

1. **hash field 不能单独设 TTL。** 官方明确说，hash 里的字段没有独立的过期时间，只能是整个 key 一起过期。如果你的业务要求每个对象独立过期，这个优化就不能直接用。
2. **超过阈值会退化。** field 数或 value 大小超过配置后，hash 会转成真正的哈希表，省内存的效果消失。改阈值前要压测转换耗时。

**怎么判断自己有没有大 key：**

```bash
# 扫描各类型中最大的键（内部用 SCAN，不会一次性阻塞）
redis-cli --bigkeys

# 看单个 key 占多少字节
redis-cli MEMORY USAGE shop:product:1001:detail

# 看编码是不是紧凑的
redis-cli OBJECT ENCODING shop:product:1001:detail
```

> 生产上 `--bigkeys` 也要避开业务高峰跑，它对 CPU 仍有消耗；`MEMORY USAGE` 对超大对象本身也有成本。先 `SCAN` 定位范围，再针对性深挖。

## 四、集群里的花括号：hash tag 到底在干什么

上了 Redis Cluster 之后，很多人才第一次听说 `CROSSSLOT`：

```
(error) CROSSSLOT Keys in request don't hash to the same slot
```

原因是 Cluster 把数据分成 **16384 个槽（slot）**，每个 key 按公式算落到哪个槽：

```
HASH_SLOT = CRC16(key) mod 16384
```

而事务（MULTI/EXEC）、Lua 脚本、`MGET` / `MSET` 这类**多 key 命令**要求所有 key 必须在同一个槽。两个 key 算出来槽号不同，就报错。

**hash tag 是这个规则的唯一例外**：如果 key 里有一段合法的 `{...}`，Redis 只对花括号里的内容做 CRC16。

```bash
# ✕ 算整个 key，两个不同槽
user1000.following
user1000.followers

# ✓ 都只哈希 user1000，同一个槽
{user1000}.following
{user1000}.followers
```

### 花括号不是随便写的

Redis Cluster 规范里写得很精确，三条同时满足才算有效 tag：

1. key 里有 `{`；
2. 右边有 `}`；
3. 两者之间有**至少一个字符**。

所以这几个例子结果不一样：

| key | 实际哈希的内容 | 说明 |
|---|---|---|
| `{user1000}.following` | `user1000` | 标准有效 tag |
| `foo{bar}{zap}` | `bar` | 只认第一对 |
| `foo{}{bar}` | 整个 key | 花括号里没内容，不算 |
| `foo{{bar}}zap` | `{bar` | 第一个 `}` 之前的内容 |
| `{}something` | 整个 key | 以 `{}` 开头，整串哈希 |

> **术语小抄 · CRC16**
> 一种 16 位循环冗余校验算法，这里被当作哈希函数用：同样的输入永远得到同样的 16 位数，对 16384 取模就得到槽号。它不是加密哈希，只是把 key 均匀地散到 16384 个桶里。

### 一条重要提醒：tag 是双刃剑

hash tag 解决了 `CROSSSLOT`，但**用粗了会出事**。

如果你写成 `{shop}:product:1001:stock`、`{shop}:product:1002:stock`……所有商品都被 `shop` 这个 tag 钉在同一个槽上，集群的分散能力就废了，那个分片会先被打爆。

正确做法是：**只用真正需要原子操作的最小共享单元做 tag**，比如同一个用户的 following 和 followers 用 `{user1000}`，不同用户各不相同。

## 五、上线前最后一遍检查

按这个顺序过一遍，基本不会留坑：

1. **能不能念出来？** 把 key 念给同事听，他能不能猜到是什么数据？
2. **前缀能不能扫？** 写一条 `SCAN MATCH` 能不能捞出这一类 key？
3. **长度是不是过头了？** 有没有把 URL、JSON、完整 SQL 塞进 key？
4. **格式会不会变？** 会变的话有没有 `v1` / `v2`？
5. **value 有多大？** 用 `MEMORY USAGE` 看过没有？超过几 MB 就该考虑拆。
6. **TTL 是不是都一样？** 一批 key 同时过期就是雪崩，要加随机抖动（见上一篇《缓存穿透、击穿、雪崩》）。
7. **集群下会不会 CROSSSLOT？** 多 key 操作的 key 是不是用了同一个 `{tag}`？

## 术语小抄

| 术语 | 大白话 |
|---|---|
| binary safe | key/value 是字节串，什么字符都能放，不限文本 |
| 冒号分层 | 约定俗成的命名法，Redis 本身不认层级 |
| listpack / ziplist | 小对象的紧凑连续内存编码，省内存但超过阈值会退化 |
| 大 key | value 很大的键，删除和迁移会阻塞 |
| hash tag | `{...}` 里的部分决定槽位，用来把多个 key 钉到同一个槽 |
| slot | Redis Cluster 的 16384 个数据分片单位 |
| CROSSSLOT | 多 key 命令里的 key 不在同一个槽，直接报错 |
| TTL 抖动 | 过期时间加随机数，避免一批 key 同时失效 |
| SCAN | 游标式遍历，生产替代 `KEYS` 的安全做法 |
