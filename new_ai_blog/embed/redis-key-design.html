1先解剖一个 key：它其实是一条"地址" 结构

Redis 官方文档的示例就是 SET bike:1 Deimos——用冒号把"对象类型"和"编号"分开。把这套思路扩展一层，就是生产上最好用的命名法。

怎么看：先看上面彩条，四段各管一件事；再看左下三个好处。重点是最后一句——冒号只是给人看的，Redis 眼里整串就是一个字节串。

2好 key 和坏 key：差别全在"三个月后还看得懂吗" 对比

设计 key 最实用的检验方法：把它丢给一个没看过代码的人，问"这是谁的什么数据"。答得上来就是好 key。

怎么看：左右对照着读，重点看第 2 条和第 5 条。下划线不是"错"，但它把层级拍平了；通配符永远是 查询条件，不是 key 的一部分。

3长度怎么拿捏：不是越短越省，也不是越长越清楚 内存

Redis 每个 key 都要存一份元信息（字典项、指针、过期时间等），长 key 会把这份固定开销反复放大。官方的建议是"别太长也别太短"，中间有个甜点区。

怎么看：先看三段对比，重点记甜点区的样子。下面两条数据是 Redis 官方内存优化文档的原文结论：能用一个 hash 就别用一堆 key，能用位图就别一个用户一个键。

4大 key 怎么拆：一个 10MB 的键，拖慢的是整个实例 拆分

"大 key"不是说 key 名字长，而是 value 太大：一个 Set 装几百万成员、一个 String 塞 10MB JSON。删除、迁移、AOF 重写都会卡在这一坨上。

怎么看：核心是中间那条 11 MB → 1.7 MB 的对比，这是官方文档里的真实测量。右边黄色框是代价：hash field 不能单独设过期时间，拆分前先确认你的 TTL 粒度。

5集群里的花括号：不是装饰，是"把我俩放一起" 集群

Redis Cluster 把 key 映射到 16384 个槽位。多 key 命令（事务、Lua、MGET 等）要求这些 key 在同一个槽，否则直接报 CROSSSLOT。hash tag 就是来解决这件事的。

怎么看：先读公式和例外，再对照上下两组 key。重点记最后一句：hash tag 是把双刃剑，它解决 CROSSSLOT，也可能把压力集中到同一个分片。

6落地清单：写 key 之前，先过这六关 落地

mkdir 之前想清楚目录结构，比事后 rename 便宜得多。Redis 的 key 也一样——一旦上线有数据，改名就意味着迁移。

怎么看：设计阶段六条按顺序过一遍；上线后四个命令按"先 SCAN 定位 → 再 MEMORY USAGE 深挖 → 最后决定拆不拆"的顺序用。
