SQL Server → GoldenDB：一次 CRM 迁移要过的四道关

1先看清全局：迁移要过四道关 总览

GoldenDB 兼容 MySQL 语法，不兼容 SQL Server 的 T-SQL。所以这不是"换个连接串"，而是要做结构、分片、语法、数据四次改造。

怎么看：上排四关从左到右做。左下"四个坑"是真实项目里最常见的返工原因；右下是正确顺序。记住：工具只搬数据，不改你的 SQL。

3分片键怎么选：CRM 四张表的实战答案 分片

分片键一旦定了就很难改（要重建表）。原则是：优先用查询字段、关联字段、主键或唯一索引；选很少改、值稳定的字段。

怎么看：横着读每一行。最关键的是前两行——客户表和跟进记录用同一个 cust_id 分片，这样"查某客户的详情 + 跟进记录"在本分片就能算完，不用把数据拉来拉去。

5搬数据两条路：Sloth 直连 vs Loader 摆渡 迁移

一条是管道（工具连着两端库边读边写），一条是摆渡（先把源库导成文件，再让 GoldenDB 读文件）。SQLServer 这条路两者都不支持增量。

怎么看：先看上面两条数据流：A 是一条直线连到底，B 中间多了"CSV 文件"这一站。再看每块下方的 ✓ 与 ✕：省事和可控是此消彼长的。最后蓝框——两条路都得停写，这是 SQLServer 这条路的天花板。

6Loader 摆渡全流程：从 bcp 拆批到写入 GoldenDB 重点

六步走：算主键边界 → bcp 按范围导 CSV → 文件清点 → Loader 读文件 → 失败落盘重导 → 自己写脚本校验。工具只管写，对不对要自己比。

怎么看：上排三步是"导出侧"，下排两步是"导入 + 校验"。最关键的两处：② 按主键范围拆批（不要按时间或页号），⑥ 校验自己写（Loader 只报成功/失败行数，不保证字段对）。

7割接当天：按顺序走，并且一定留回退路 落地

迁移成功不等于切换成功。割接窗口里最重要的是"可回退"——任何一步对不上，都要能原路退回去。

怎么看：左边七步按顺序做，右边回退路线是"保命符"。重点看第 ⑤ 步的灰度——先放几个用户试，别一把全切。
