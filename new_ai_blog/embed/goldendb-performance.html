1官方思路：不是先加机器，而是按顺序排雷 路线

白皮书和《中兴通讯技术》金篆数据库专题里反复出现的顺序：开发/迁移前先评估与压测，生产中先揪出慢 SQL，再看计划、分片、索引，最后用并行、读写分离和限流把稳定性兜住。

大白话：别一上来就说「数据库慢」。先像医生一样问诊：什么时候慢、哪条语句慢、扫描了多少数据、有没有跨节点搬货。证据齐了再开药。

2慢 SQL 常见的三宗罪 定位

官方文章指出：缺索引会生成低效计划，慢 SQL 会挤占 CPU、内存和 I/O；分布式下还要额外看「数据是不是被跨节点搬运」和「执行计划是不是选错了」。

术语：全表扫描 = 没按目录找书，把整本书逐页翻；笛卡尔积 = 两张表没写关联条件，行数被乘成爆炸式增长；DML = 增删改，DQL = 查。

3让计算靠近数据：下推与代价优化 优化器

官方优化器分两层：逻辑优化用 RBO（基于规则的优化），物理优化既有 RBO 也有 CBO（基于代价的优化）。目标都是少搬数据、少做无用计算。

大白话：别把一车货拉到前台再挑，直接在每个仓库先挑好、称好，只把结果报给前台。COST 就是优化器给每条路算的「过路费」。

4分片键选错，关联查询就累 分片

官方建议把业务关系密切的多张表采用相同分片，避免跨节点请求；无法同分片时用全局索引做分片键转换；不常改的小表用复制策略（广播表）复制到每个分片。

注意：官方也提醒，SKIP SCAN 这类索引跳跃扫描要满足「前导列基数低、非前导列选择性高」，乱用反而有性能风险。

5看图开药：EXPLAIN → 索引推荐 → 绑定计划 诊断

官方支持查看 CN 计划、DN 计划或两者同时输出；支持 hint 和 outline 在线绑定执行计划；索引推荐是内核原生能力，用直方图采样，亿级大表 10 秒内出报告。

术语：hint 是给优化器的小纸条，提示它走某条路；outline / SQL Profile 是把好计划「钉住」，以后都按这条路走；COST 是优化器算出来的代价估算。

6兜底组合：分流、并行、批量、限流 稳定性

当 SQL 和结构都调过，官方还会用读写分离、自动并行、流式查询、批量协议、SQL 限流和 TP/AP 异步隔离，把高并发下的响应时间与稳定性兜住。

术语：TP（OLTP）= 一笔笔短平快的交易；AP（OLAP）= 复杂统计分析；HTAP = 一套系统同时干这两件事。Auto-DOP 就是自动决定「这事派几个人并行干」。
