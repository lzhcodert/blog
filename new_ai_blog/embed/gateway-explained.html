网关：所有请求都得先过这道门

它不是"多一层转发"，而是把每个服务都要重复做一遍的事——验身份、限流量、找位置、记日志——从业务代码里搬出来，只在门口做一次。六张图，从协议定义讲到生产事故。

它是什么南北与东西四层与七层一次请求网关家族生产坑

1它对外冒充服务器，对内只是个转发员 概念

RFC 9110 把 gateway 直接等同于 reverse proxy：对客户端而言它就是源站，收下请求后翻译一下，再转给内部真正干活的服务器。

关键区别：代理是客户端自己配的（帮你出门），网关是服务端自己装的（替服务器挡门）。这就是为什么网关又叫"反向代理"——方向反过来了。

2南北向与东西向：同一个词，两个位置 位置

外部用户进来的流量叫南北向，服务之间互相调的流量叫东西向。这两段该用不同的东西管，混用是生产里最常见的架构错位。

一句话：南北向是"门"，东西向是"楼道"。门要查证件，楼道只需要保证跑得快、断了能绕。Istio 官方文档明确说，gateway 配置作用在"跑在网格边缘的独立 Envoy 代理"上，而不是服务旁边的 sidecar。

3四层看信封，七层拆开信看内容 能力

四层只认 IP 和端口，七层能读到 HTTP 方法、路径、Header。能不能按 path 路由、按 header 灰度、按用户鉴权，全取决于它站在哪一层。

记法：四层像邮局，只看信封地址就能投递；七层像前台，拆开看内容，才知道该转给哪个部门、要不要先登记。

4一个请求过关的八道工序 流程

顺序不是随便排的：先做便宜的判断（TLS、路由），再做贵的（鉴权、限流），最后才转发。搞反顺序，等于让垃圾流量先消耗最贵的资源。

大白话：这八道工序，以前是每个业务服务各写一遍，写八份、改八次、错八个地方。放到网关，是写一份、改一次、全站生效——这才是网关真正的价值，不是"多一层转发"。

5都叫"网关"，其实是五个工种 选型

负载均衡、流量网关、API 网关、BFF、服务网格经常同时出现在一张架构图上。分不清它们的边界，就会出现"两个网关互相甩锅"的排障现场。

Kubernetes 的答案很值得抄：官方把网关拆成三个角色——GatewayClass 定"谁来提供"，Gateway 定"这一处入口实例"，HTTPRoute 定"怎么路由"。基础设施团队管前两个，应用团队只写 Route。职责分清，才不会互相等排期。

6六个坑，几乎每个团队都踩过 生产

网关上线不难，难的是它成为唯一入口之后，所有的超时、重试、IP、容量问题都会在这里集中爆发。

排查顺序：先看网关自己的指标（QPS、4xx/5xx、上游连接数、CPU），再看上游服务的耗时。网关 5xx 且上游无日志，多半是连不上或超时；网关 4xx 且上游无日志，多半是鉴权或限流拦下的——责任划分清楚了，才不用半夜拉三个团队开会。
