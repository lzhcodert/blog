1没有锁会出什么事：三步的加一，被插成了负数 第一问

Java 官方的经典例子：c++ 看着是一行，其实是读、加、写三步。两拨人同时做，结果就丢了。

怎么看：先看时间线的第 5、6 行——甲写入 1，乙随后写入 -1，甲那一次加一凭空消失。再看下面三个框：交错是「同时改」，看不见是「改了对方不知道」，跨机器是「连同一块白板都没有」。锁就是为解决这三层麻烦而生的。

2锁的原理：四步动作、三条底线、两个附加服务 第二问

所有锁都是同一套动作。锁的不是代码，而是大家约定共同看一眼的那个「标记」。

怎么看：上排四张卡片从左到右读，注意是「先抢牌子再进屋」，不是「进屋再找牌子」。中排三条底线里最容易被忽略的是「不死等」——所以分布式锁必须设过期时间。下排两个附加服务提醒你：锁不只防冲突，还负责让下一个人看见正确结果。

3单机锁：牌子挂在进程自己家里 第三问 · 上

同一个 JVM 里的线程共享一块内存，牌子就挂在内存里。换个对象、换台机器，牌子就不认了。

怎么看：左图重点是牌子只有一块：三条线里只有甲是实线拿到牌子，乙丙在门口等。右图两个反例都要记住——「每次 new 一个新锁对象」和「三台机器各锁各的」，本质上都是「大家看的不是同一块牌子」。最后一行就是单机锁和分布式锁的分水岭。

4分布式锁：牌子换成所有人都能查的云上登记册 第三问 · 下

Redis 官方给的正确姿势：SET 时带唯一值和过期时间，释放时校验值匹配才删。

怎么看：先看三条箭头都指向同一个 Redis 框——这就是「同一块牌子」在分布式里的样子。中间那条命令三个参数各管一件事：NX 管抢、PX 管崩溃后自动释放、随机值管别删错人。下面左右两栏对照，重点看右栏的四步翻车链：卡顿 → 过期 → 别人抢 → 误删。

5再进一步：主从切换会丢锁，栅栏令牌才是底牌 第三问 · 补充

Redis 官方自己列了四步翻车；Kleppmann 指出就算锁完美，停顿和延迟也能破坏互斥。

怎么看：上半部分按箭头读四步，重点在第②步「还没同步就宕机」——这是 Redis 官方承认的竞态。中间三框说明锁服务再完美也没用，因为问题出在客户端停顿和时间上。最下面 33 → 34 → 33 的序列是整张图的关键：最后那次写入被存储层拒绝，才是真正的安全底线。

6什么时候需要锁：先过三问，再看用哪种 第四问

三个问题全是「是」才需要考虑锁。能靠数据库唯一约束或版本号解决，就别再套一层锁。

怎么看：上排三个框从左到右过一遍，任何一个答「否」就别急着加锁。中间左右对照：左栏是锁的主场，右栏是「不需要锁」的清单——尤其最后一条，数据库约束往往比再加一层 Redis 锁更可靠。下排那两句决定了你的技术选型：只为效率，简单就好；为了正确性，锁只是第一道防线。
