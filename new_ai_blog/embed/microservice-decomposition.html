微服务怎么拆：四刀下去，别把复杂度挪到会议桌

用一家网上超市走一遍：切什么、切多大、边界在哪、数据怎么分。六种常见切法与落地顺序都在下面六张图里。

1第一刀：按技术层切，还是按业务能力切 总览

服务数量不是重点。重点是「加一个需求，要惊动几个组」。按技术层切，一个需求横穿三层；按业务能力切，一个组从头做到尾。

怎么看：先看左右两栏第三条横排文字的位置差。左栏「到货通知」要横穿 UI、服务端、DBA 三层；右栏同一个需求落在库存组一个格子里。判据不是服务数量，是一次需求要协调几个组。

2从价值链找业务能力，再分出三六九等 方法

业务能力是「企业为创造价值而做的事」，不是「系统有哪些页面」。价值链每个环节都要有能力托住，能力再按 core / supporting / generic 区分投入。

怎么看：先从上往下对一遍：价值链上的每个环节，下面是否真有一个能力托住。「售后」找不到对应能力，说明业务设计有缺口，跟技术无关。再看最下面三档分类：给短信通知配三人小队，是常见的浪费。

3第二刀：切多大——不是越小越好 尺度

microservices.io 给的尺度是「两个披萨团队」6~10 人，能独立开发、测试、部署。Fowler 补了一条更好用的合并判据：总是一起改的两个服务，就该合并。

怎么看：重点看中栏和右栏的第三行：中栏「大多只动一个服务」，右栏「动三四个服务」。判断服务大小别数代码行数，翻一下最近半年的提交记录——两个服务是否总在同一批需求里一起改。

4第三刀：边界画在哪——同一个「商品」不是一个意思 DDD

大系统做领域模型的完全统一，既不可行也不划算。DDD 的做法是划成一个个限界上下文：每个范围内术语自洽，跨出去做映射，而不是硬共用一张表。

怎么看：逐框读第三行的问题，四个问题各自只属于一个部门。特别注意 B 框：订单里的商品是下单那一刻的快照，商品改价不能改历史订单——这不是冗余，是「当时的事实」。这是限界上下文最直观的价值。

5第四刀：数据必须跟服务走 验证

每个服务的数据私有，只能通过它自己的 API 访问。这是判断真假微服务最容易验证的一条。代价是跨服务事务和跨库查询都要另想办法。

怎么看：左边四根红线都指向同一张大表，右边四根绿线分别指向四个 schema。注意「共用服务器」不等于「共用数据库」——同一台 MySQL 上做 schema 隔离是合格做法。真正要防的是绕过 API 直连别人的表。

6落地：别停机重写，用绞杀者模式逐步换 演进

「照原样重写一次切过去」大多数时候会烧得一塌糊涂：用户等不了、旧行为搞不清。绞杀者做法是让新功能长在旧系统外面，一块块搬，最后旧系统只剩空壳。

怎么看：看每张卡片最下面那一组小方块：旧单体（灰）从满格变成空壳，新服务（绿）从无到有。第 4 步的「过渡层」常被嫌浪费，但它换来的低风险和更早收益，通常比成本高。
