前面两篇讲了 GoldenDB 的架构和效率优化。这篇专攻一件事：**当一笔交易要同时改好几个分片上的数据，GoldenDB 怎么保证不出错？**

拿银行转账举例最直观：A 账户在 DN1，B 账户在 DN2，A 给 B 转 50 元。最怕的就是 A 扣成功了、B 加失败了——钱凭空消失。单机数据库靠本地事务轻松解决，跨机器就没那么简单了。

## 一句话版本

**给每笔写交易发一个全局工单号（GTID），CN 派活让各 DN 分头改，改完统一提交；万一有人提交失败，就照着 binlog 把已经改成功的那侧原样改回来；读的时候再看一眼「哪些工单还没最终生效」，跳过它们。**

官方把这套机制的目标叫**强一致性**：用户完成数据更新后，后续所有读操作都能且只能读到更新以后的值。

## 单机事务为什么不够用

单机数据库里，事务（Transaction）就是「要么全做，要么全不做」。它靠三个性质撑住：ACID——原子性（A）、一致性（C）、隔离性（I）、持久性（D）。

一笔交易跨了多个 DN 之后，麻烦变成三个：

1. **原子性难**：A 那台成功了、B 那台失败了，谁来把已经成功的撤销？
2. **隔离性难**：别的交易正在读，怎么知道眼前这行数据是「已经算数」的版本，还是别人改到一半的？
3. **故障恢复难**：机器、进程、网络出问题后，怎么知道当时有多少事务还在半路上？

官方白皮书 4.1 开门见山：GoldenDB 作为事务型数据库，支持集群所有节点间事务的 ACID 特性，保证故障可恢复，以及恢复后满足 ACID 要求，并负责节点的并发控制。

## 四位主角：发号的、派活的、干活的、纠错的

| 角色 | 官方定位 | 大白话 |
|---|---|---|
| GTM 全局事务管理器 | 生成 / 释放 GTID，维护活跃事务及当前活跃 GTID 快照，管 ID 生命周期 | 发号员兼登记员：给每笔写交易发唯一工单号，并记下谁还没办完 |
| CN 计算节点 | 分布式事务协调者，基于改进的两阶段提交协调多个资源域内的本地事务 | 包工头：拆活、派活、盯进度、把状态报给 GTM |
| DN 数据节点 | 最终存储，执行本地事务，写 binlog | 仓库管理员：真正在自己那片账本上改数 |
| DBAgent | 提交失败时解析 binlog 中是否含有异常事务的 GTID，构造反向回滚语句 | 事后纠错员：拿着监控录像把改错的货搬回原位 |

这里最容易被忽略的是 **DBAgent**。普通两阶段提交遇到「有的参与者已经提交了」会很棘手；GoldenDB 的厉害之处恰恰是「已提交事务也能自动回滚」，而这件事是 DBAgent 靠 binlog 反解做出来的。

## 协调全流程：六步走

下面按官方白皮书 4.1.2 的控制链路拆开讲（文末第 2 张图把六步画在了一起）。

### 第 1 步：向 GTM 申请 GTID

CN 在处理分布式写事务时，先向 GTM 申请一个**全局唯一且递增的整数**作为 GTID（Global Transaction ID，全局事务 ID）。官方还说：为了减少 CN 和 GTM 的交互次数，把「申请单个」优化成了**批量申请**，「释放单个」也优化成了**批量释放**。

> 大白话：不是每笔业务跑一趟发号窗口，而是一次领一沓 numbered 工单，用完一起还。

### 第 2 步：把 GTID 写进每条记录

GoldenDB 在**所有表里增加一个 GTID 隐含列**（隐藏字段，业务看不见）。更新数据时同步更新这一列，把它作为分布式环境下的「全局锁」。

> 大白话：每一笔货都贴上工单号。后面不管是谁来查、谁来纠错，看标签就知道它是哪笔交易留下的。

### 第 3 步：CN 下发本地事务

CN 生成分布式执行计划，按分片规则把子任务下发给对应 DN。各 DN 在自己这片数据上执行本地事务——A 在 DN1 扣钱，B 在 DN2 加钱。

### 第 4 步：统一提交，状态实时记 GTM

官方原话：**计算节点作为分布式事务协调者，基于改进的两阶段提交（2PC）方法，协调多个资源域内的本地事务，同时将全局事务状态实时记录在全局事务管理器中**。所有 SQL 执行完之后，各 DN 统一 COMMIT。

### 第 5 步：失败就补偿回滚

如果某个 DN 的 COMMIT 失败，其他节点上的 **DBAgent 解析 binlog**，找出带有这个异常事务 GTID 的改动，**构造反向 SQL** 下发给 DN 执行回滚。官方银行方案把这项能力直接写成「全局事务管理器和已提交事务自动回滚相结合」。

> 大白话：binlog 是「改动流水账」。反解就是读流水账发现「9527 号把 A 减了 50」，自动生成「把 A 加回 50」的反向操作。

### 第 6 步：让后续读看到正确版本

写事务收尾了，读事务还有一关：SELECT 发起时，CN 从 GTM 拿到一份**全局活跃事务名单** `active_gtm_gtid_list`，带到 DN 做可见性判断：

- 行上的 GTID **不在**名单里：改动已经全局可见，直接返回当前数据；
- 行上的 GTID **在**名单里：改它的人还没尘埃落定，就通过 undo 构造前像，继续往前找，直到找到全局可见的版本。

这就是分布式 MVCC。单机 MVCC 看的是本地活跃事务，GoldenDB 多带了一份全局名单——这正是「分布式」三个字贵的地方。

## 改进的两阶段提交，到底改在哪

标准 2PC（白皮书 4.3.7 把它放在 XA 章节里讲）分两步：**准备阶段**，协调者问所有参与者准备好了没；**提交阶段**，全就绪就一起提交，任何一个失败就一起回滚。

GoldenDB 的「改进」可以理解成加了三样东西：

1. **GTID 全局锁**：每行记录带 GTID，不只判断谁改了，还判断这一版算不算数；
2. **状态实时写 GTM**：协调者不只自己记进度，还把全局事务状态实时记到 GTM，便于统一判断与恢复；
3. **已提交事务自动回滚**：普通 2PC 最怕「已经 COMMIT 了怎么撤」，GoldenDB 靠 binlog 反解构造反向 SQL，把已提交的改动也补偿回来。

另外，官方明确 XA 协议**没有描述如何实现分布式事务的隔离性**，隔离性是由每个资源管理器（RM）的本地事务隔离性来保证的。GoldenDB 自己的分布式事务则用 GTID + 全局快照把这一层补上了。

## 官方转账例子：A 成功、B 失败

白皮书 4.1.2 给的例子和文章开头一样：A、B 原来各有 100 元，A 给 B 转 50 元，两人属于不同节点。

1. A 在本地执行更新成功：100 → 50，行上写入 GTID，COMMIT 成功，binlog 留下痕迹；
2. B 的加钱操作失败，进入**单机事务异常回滚**流程，B 保持 100；
3. A 虽然已经提交，但进入**已提交事务回滚**流程：各方 DBAgent 解析 binlog，发现带该 GTID 的改动，构造反向 SQL 下发；
4. A 被加回 50，回到 100。

结果：A = 100，B = 100。钱没有凭空消失。官方把这条路径总结为「通过已提交事务回滚，解决分布式一致性问题」（文末第 4 张图完整画了这条链路）。

## GTM 自己出问题怎么办

协调者依赖的 GTM 如果挂了，整套机制就会停摆。官方给了两层保障：

- **主备架构**：GTM 采用主备部署，主节点异常时自动切到备节点继续提供服务；
- **集群 + 租户绑定**：进一步扩展为 GTM 集群架构，多个 GTM 和多个租户（Tenant，即相互隔离的数据库实例）绑定，某个 GTM 切换时**只影响它绑定的租户**，其他租户照常跑。

备份恢复也考虑到了事务状态：官方 4.5.3 说，备份包含运行日志**以及每个时刻的全局事务列表快照**，因此可以恢复出一个全局一致性的数据快照。换句话说，不只记「数据长什么样」，还记「当时谁在办事」。

## 隔离级别与 XA 接口

- 官方支持**读未提交、读已提交、可重复读、串行化**四种隔离级别，推荐使用 **Read Committed**。还支持隐式启动事务、默认 `auto_committed=0`、设置 `savepoint` 做更细粒度的并发控制；
- XA 方面，GoldenDB 提供的 JDBC 驱动支持标准 XA 接口，兼容 Oracle 的 XA 事务，支持 `XA START / END / PREPARE / COMMIT / ROLLBACK / RECOVER` 等指令；在 XA 场景中 GoldenDB 服务器充当**资源管理器（RM）**，客户端程序充当**事务管理器（TM）**，提交阶段用两阶段提交保证原子性。

要注意区分：GoldenDB 自带的分布式事务机制（GTM + GTID）和它对外提供的 XA 接口是两回事——前者是内部怎么协调，后者是外部应用怎么接入这套协调。

## 术语小抄

| 缩写 / 术语 | 大白话 | 在本文里的作用 |
|---|---|---|
| 事务 Transaction | 要么全做、要么全不做的一组操作 | 转账必须整体成功或整体失败 |
| ACID | 原子性、一致性、隔离性、持久性 | 官方承诺集群所有节点间事务都满足 |
| GTID | 全局唯一且递增的事务号 | 贴在每行数据上的工单号 |
| GTM | 全局事务管理器 | 发号、释放、维护活跃事务与快照 |
| CN | 计算节点 | 事务协调者，派活并上报状态 |
| DN | 数据节点 | 执行本地事务、真正落盘 |
| DBAgent | 节点上的代理组件 | 解析 binlog 构造反向 SQL 做补偿 |
| 隐含列 | 表里看不见的字段 | 每行记录都带 GTID |
| 2PC | 两阶段提交：准备 + 提交 | 跨节点统一提交的协议 |
| 已提交事务回滚 | 已经 COMMIT 了也能撤回来 | 解决「有人成功有人失败」的死局 |
| binlog | 数据改动的流水账 | 反推出反向 SQL 的依据 |
| 反向 SQL | 把改动抵消掉的 SQL | A 减了 50，就生成「A 加 50」 |
| MVCC | 多版本并发控制 | 读不加锁，读写不冲突 |
| undo 前像 | 修改前的旧版本数据 | 活跃改动要跳过时沿它往前找 |
| active_gtm_gtid_list | GTM 给出的活跃事务名单 | 判断这行数据现在算不算数 |
| 强一致 | 更新完成后，后续读只能读到新值 | 官方对一致性的承诺 |
| Read Committed | 读已提交隔离级别 | 官方推荐的默认用法 |
| savepoint | 事务里的中途存档点 | 可以只回滚到某个点 |
| XA | 分布式事务的标准接口 | GoldenDB 兼容，可作为 RM 接入外部 TM |
| RM / TM | 资源管理器 / 事务管理器 | XA 模型里的被协调方与协调方 |
| 租户 Tenant | 相互隔离的数据库实例 | GTM 集群按租户绑定，故障隔离 |
| auto_committed | 是否自动提交 | GoldenDB 默认 0，即不自动提交 |

GTM 发号、CN 派活、DN 干活、DBAgent 纠错；已提交也能靠 binlog 反解回滚，读的时候拿全局活跃名单过滤版本——这就是 GoldenDB 把单机事务那套「要么全做要么全不做」搬到一群机器上的办法。
